## 1. Overblik over arkitekturen
```
┌─────────────────┐        ┌──────────────────┐        ┌─────────────────┐
│   Sportmonks     │──────▶│  Vercel Function  │──────▶│    Supabase      │
│  (football data) │        │ /api/sync-matches │        │ (database + auth)│
└─────────────────┘        └──────────────────┘        └─────────────────┘
                                                                  ▲
                                                          ┌──────────────┐
                                                          │  React-app    │
                                                          │ (Vercel-hosted)│
                                                          └──────────────┘
                                                                  ▲
                                                            Brugere (browser)
```
Frontend: React + Vite, rent `fetch`-baseret mod Supabase (ingen SDK). Koden er opdelt i moduler under `src/`: `lib/` (`supabase.js` = REST-klient/auth, `scoring.js` = point/runde-helpers, `data.js` = alle async-loaders, `analytics.js` = fire-and-forget hændelseslogning + dashboard-loaders + liga-diagnosen, `analyticsMetrics.js` = måle-ordbogen bag dashboardets ⓘ, afsnit 21), `ui/` (`theme.js` = designtokens/styles, `components.jsx` = delkomponenter, inkl. `StatTile`/`StatGroup`/`MiniBars`/`StateChip`/`SignalRow`/`PctGrid`), og `screens/` (én fil pr. fane/skærm + `MainApp.jsx` = shell/navigation + `AnalyticsPanel.jsx` = Admin → Analytics). `App.jsx` er en tynd rod, der booter session/auth. Mobil-first: 5-fane bundnavigation (Hjem · Tip · Ligaer · Championship · Rating), maks. bredde ~430 px centreret (se afsnit 7).
Hosting: Vercel (Hobby-plan). Auto-deployer ved hver commit til GitHub (se afsnit 11).
Database + login: Supabase (Postgres + Auth), tilgået via REST/PostgREST. Frontenden bruger en offentlig `publishable`-nøgle, hårdkodet i `src/lib/supabase.js` (som fallback, hvis `VITE_SUPABASE_URL`/`VITE_SUPABASE_KEY` ikke er sat — se afsnit 9) — det er by design (nøglen er offentlig og beskyttet af RLS).
Fodbolddata: Sportmonks API (gratis plan). Planen dækker fire turneringer: Superliga (`271`), Superliga Play-offs (`1659`), Scotland Premiership (`501`) og Premiership Play-Offs (`513`) — kun ligaer i planen kan synkroniseres. Premier League/Champions League kræver abonnement; se beslutning A10 (31. juli 2026) i [`docs/DECISIONS.md`](docs/DECISIONS.md) og [`docs/features/turnering-2.md`](docs/features/turnering-2.md) §3.4.
PWA: `manifest.json` + ikoner i `public/`, så appen kan tilføjes til hjemmeskærmen som en rigtig app. Manifest og ikoner følger appens mørkeblå tema (`#0C1622` + guld pokal).
Kildekode: GitHub-repository `Nikkelajsen/Prediction-Champ`.

## 2. Database-skema
Tabel	Formål
`leagues`	Ligaer. **`provider`** = datakilden (`sportmonks` → numerisk liga-id, `footballdata` → turneringskode som `PL`/`CL`); `api_league_id` er ligaens id hos netop den. **`live_enabled`** styrer, om ligaens kampe overhovedet må vises som i gang — det følger abonnementet, ikke leverandøren (afsnit 8). `is_visible` styrer om ligaen vises for almindelige brugere (admin ser altid alt).
`seasons`	Sæson pr. liga. `api_season_id` gemmes automatisk af sync-funktionen første gang, så fremtidige kørsler ikke behøver navne-opslag. Betydningen følger leverandøren: et sæson-id hos Sportmonks, STARTÅRET (`2026`) hos football-data.org.
`teams`	Hold. `api_team_id` = holdets id hos ligaens datakilde, sat automatisk — præfikset `fd:` for football-data.org (se id-præfikset i afsnit 8). Tabellen er scopet til `league_id`, så samme klub i to turneringer er to rækker.
`matches`	Kampe. `round_key` (tirsdag–mandag, auto-beregnet), `home_score`/`away_score` (**endeligt** resultat — `not null` betyder "kampen er spillet"), `stage_name` (leverandørens rå stage-navn, fx "Regular Season"/"Championship Round"/"Relegation Round" — se afsnit 8/10), `api_fixture_id` (unik). Desuden live-kolonnerne `live_home_score`, `live_away_score`, `live_state`, `live_minute`, `live_updated_at` (`sql/live_scores.sql`), der viser den *nuværende* stilling mens kampen spilles og aldrig giver point — se afsnit 8.
`profiles`	Brugerprofiler. `display_name`, `is_admin`, `created_at` (tilmelding, backfillet fra `auth.users`), `last_seen_at` (senest aktiv, sat af `touch_activity()`). `display_name` er unikt (case-insensitivt) — se afsnit 6.
`competitions`	`mode` ∈ `full_season / team / time_range / custom / random`. `league_id`/`season_id` er nullable — `custom` og `random` kan spænde over flere ligaer. `group_id` (nullable, `on delete set null`) = liga-tilhør (liga-laget, afsnit 18); `null` = liga-løs konkurrence. `rules` (jsonb) indeholder pointregler og skrives altid som `{ exact: 3, outcome: 1 }` — `openDaysBefore` (det rullende gætte-vindue) er fjernet august 2026 og læses ikke længere; nøglen kan stadig ligge i gamle rækker, hvor den er inert.
`competition_participants`	Deltagere. `hidden` = brugerens egen arkivering (påvirker ikke andre deltagere). **`hidden` gælder kun LIGA-LØSE konkurrencer** — kun der findes Arkivér/Gendan (`LigaerTab`). For konkurrencer i en liga ignoreres flaget (`MainApp.loadCompetitions`: `_hidden = c.group_id ? false : hidden`), så et forældet flag fra før en flytning (`move_competition_to_group`) ikke skjuler en tilmeldt konkurrence på Hjem/Tip, mens liga-siden viser den som "Med". DELETE-policy (liga-laget, `sql/group_membership_invariant.sql`): man kan framelde sig en konkurrence, når **enten** alle konkurrencens kampe har resultat (forløbet er forbi og kan ikke skjules), **eller** man ingen tips har på allerede låste kampe. Den oprindelige regel var kun den sidste gren og var derfor i praksis permanent — se afsnit 18.
`groups`	Liga-laget: den permanente liga-enhed (fællesskabet). `name` (2–40 tegn), `invite_code` (unikt, ét delbart link pr. liga), `created_by`. UI kalder den en "liga"; `leagues` (fodbold) hedder en "turnering". Se afsnit 18.
`group_members`	Medlemskab af en liga. Nøgle `(group_id, user_id)`, `role` ∈ `admin / member`. RLS via `security definer`-funktionen `is_group_member()` (undgår rekursion). Se afsnit 18.
`competition_matches`	Hvilke kampe hører til hvilken konkurrence.
`competition_awards`	Lokale kåringer (A22, `sql/competition_awards.sql`): "Ugens bedste" (`period_type = 'round'`, `period_key` = runde-nøglen) og "Månedens bedste" (`'month'`, `'YYYY-MM'`) i konkurrencer med `mode_params.awards = true`. PK `(competition_id, period_type, period_key, user_id)`; delt førsteplads = én række pr. vinder med `shared = true`; `stats` (jsonb: exact/outcome/matches/goal_error). RLS: SELECT kun for konkurrencens deltagere, **ingen skrive-policies** — kun `award_competition_periods()` skriver. Kåringer er frosne (`on conflict do nothing`).
`predictions`	Én forudsigelse pr. bruger pr. kamp, delt på tværs af konkurrencer.
`ratings`	Aktuel Prediction Champ Rating pr. bruger. Nøgle `(user_id, scope)`. Se afsnit 5.
`rating_history`	Rating-snapshot pr. bruger pr. runde. Kolonner: `user_id`, `scope`, `round_key`, `rating_after`, `delta` (rundens ratingændring), `round_score`, `matches_predicted`, `rnk`. Se afsnit 5.
`monthly_standings` (view)	Live-view der beregner månedsligaens stilling direkte fra `predictions` + `matches`. Se afsnit 5.
`round_standings` (view)	Live-view med rundeligaens stilling pr. `round_key` (`sql/standings_tiebreakers.sql`). Se afsnit 5.
`season_standings` (view)	Live-view med sæsonchampionship-stillingen pr. `season_id` (`sql/standings_tiebreakers.sql`). Se afsnit 5.
`push_subscriptions`	Web Push-abonnementer, én række pr. enhed/browser der har slået notifikationer til. RLS: kun egne rækker. Se afsnit 16.
`notification_log`	Log over sendte push-beskeder pr. bruger (`user_id`, `key`), så samme besked aldrig sendes to gange. Kun serverfunktionen læser/skriver. Se afsnit 16.
`user_activity_days`	Aktivitets-sporing til brugerstatistik: én række pr. bruger pr. aktiv dag (`user_id`, `day`, PK begge). Skrives af `touch_activity()` ved app-start. RLS slået til uden policies — læses/skrives kun via `security definer`-funktioner. Se afsnit 15.
`analytics_events`	Analytics v1: hændelseslog (`event_id`, `event_name`, `user_id` default `auth.uid()`, `group_id`/`competition_id` nullable, `metadata` jsonb, `created_at`). RLS: kun INSERT af egne rækker — ingen SELECT/UPDATE/DELETE for almindelige brugere. Skrevet fire-and-forget fra klienten (`logEvent`/`logEventOnce` i `src/lib/analytics.js`), læst kun via admin-gatede RPC'er. Se afsnit 21.
`stories`	Story Engine-historier pr. bruger pr. runde (`user_id`, `round_key`, `competition_id` nullable, `rule`, `priority`, `league_size`, `payload`, `headline`, `body`, `dismissed_at`). Skrives kun af `generate_stories()`. RLS: læs/afvis kun egne. Se afsnit 17.
`latest_story` (view)	Præcis én kandidat pr. `(user_id, round_key)`: laveste `priority`, dernæst største liga (`league_size`), dernæst `competition_id`. Se afsnit 17.
RLS-hovedregel for `predictions` (vigtig, rettet i patch 10): man kan altid læse sine egne forudsigelser; andres kun for kampe, der er låst. Dette forhindrer snyd (at kigge andres gæt inden man selv tipper). **Låsning er per kamp** (`A21`, 1. august 2026, jf. `sql/predictions_match_lock.sql`): en kamp låser 1 time før sit *eget* kickoff, eller så snart den har fået resultat. Reglen er i SQL `kickoff_at <= now() + interval '1 hour'`, og frontenden bruger samme regel via `isLocked(match)` i `src/lib/scoring.js`. Så tipper alle på samme vidensgrundlag **for den enkelte kamp**: andres gæt bliver først synlige i det øjeblik, kampen låser, og der kan ingen længere rette sit eget. Låsen var før scopet på `(season_id, round_key)`, så rundens tidligste kickoff låste hele runden — fredagens kamp låste dermed søndagens. Se afsnit 3 for hvad der blev givet op, og hvorfor. **Null-semantikken står eksplicit i hvert udtryk:** rundereglen var null-sikker af sig selv (en runde uden kendte kickoffs havde ingen kamp inden for vinduet), men per kamp findes der ingen indre delmængde at falde tilbage på — en kamp uden kendt kickoff er derfor åben for skrivning og ikke synlig for andre.

**Låsen gælder alle fire operationer** — også skrivning (indført i `sql/predictions_write_lock.sql`, juli 2026; udtrykket er siden afløst af `sql/predictions_match_lock.sql`). Det oprindelige script lagde kun runde-låsen på SELECT og DELETE og bad i sin egen slutkommentar om to trin i hånden bagefter; ingen af dem var udført, så `"insert own predictions"` og `"update own predictions"` krævede kun `user_id = auth.uid()`. Låsen fandtes altså kun i frontenden for skrivninger, og et tip kunne stadig POST'es/PATCH'es via PostgREST efter runden var låst. Nu bærer alle fire policies det **samme** låse-udtryk (UPDATE i både `using` og `with check`, så en række ikke kan flyttes til en låst kamp ved at ændre `match_id`), og den forældede `"read predictions"`-policy er ryddet op. Skriv aldrig udtrykket om ét sted — kopiér det, ellers driver de fire policies fra hinanden. Samme udtryk bæres af `comp_participants_delete_own_unlocked` (framelding må ikke slette historik), så den skal med, hver gang låsen ændres — det er den, der overses.

## 3. Konkurrence-modes
Mode	Dansk navn (`MODE_LABELS`, `scoring.js`)	Beskrivelse
`full_season`	**Sæson**	Hele den valgte turnerings sæson — også de kampe, der først skemalægges senere (efterfyldes, se nedenfor). Vælges kun én turnering, bindes konkurrencen til den (`league_id`/`season_id` sat). Vælges flere (fx Superliga + Premier League), bliver den liga-løs (`league_id`/`season_id` = `null`, som `custom`/`random`), og de valgte turneringer gemmes i `mode_params.tournaments` (`[{ league_id, season_id }]`). Kampene materialiseres i alle tilfælde i `competition_matches` pr. turnering, så læse-stierne (stilling, tips) virker uændret
`team`	**Favorithold**	Alle kampe med de valgte hold. Ét hold: bundet form (`league_id`/`season_id` sat, `mode_params.team_id`). Flere hold — også på tværs af turneringer (A22): liga-løs med `mode_params.team_ids` (alle holdene) OG `mode_params.tournaments` (så efterfyldningens `coversSeason()` virker uændret)
`time_range`	**Periode**	Alle kampe i et datointerval i én turnering. Oprettes efter A22 via Custom-kortets "Periode"-valg; mode-værdien er uændret, så reglen stadig kan efterfyldes
`custom`	**Custom**	Håndplukkede kampe, valgt på tværs af alle synlige ligaer, med liga-filter i vælgeren
`random`	**Quick Pick** / **Quick League**	Tilfældige kampe fra de nærmeste kommende runder, med mulighed for at afgrænse til bestemte ligaer. `mode_params.count` er antal kampe **pr. runde**; `mode_params.rounds` (skrives kun når > 1) er antal runder frem — med feltet hedder konkurrencen **Quick League**, uden (eller = 1) **Quick Pick** (`modeLabel(mode, mode_params)`). Antallet begrænses automatisk til hvad der reelt er tilgængeligt
`custom` og `random` sætter `league_id`/`season_id` til `null` på konkurrencen — de er ikke bundet til én liga.
Opret-flowet er galleri-først (A22, 1. august 2026 — spec: `docs/features/opret-flow-v2.md`): skærmen viser SEKS kort (Sæson, Favorithold, Quick League, Quick Pick, Ugens kupon, Custom), som oversættes til de fem modes plus `mode_params` i `src/lib/createTypes.js` — `competitions_mode_check` er urørt, og ingen eksisterende række er migreret. "Ugens kupon" er `random` med preset (8 kampe, næste runde, alle turneringer) og genereret navn; det er det eneste kort med forudfyldt navn.
Lokale kåringer (A22/`I13`): et tilvalg ved oprettelsen ("Kår Ugens og Månedens bedste undervejs" — kun flerrunde-typer) sætter `mode_params.awards = true`. Boardet trigger derefter `award_competition_periods()` ved åbning og viser en "Kåringer"-sektion. Navnene er bevidst IKKE de globale titler: "Ugens/Månedens bedste" er konkurrencens egne kåringer, "rundevinder"/"månedsmester"/"Prediction Champ" er Championships (navnereglen i `features/turnering-2.md` §3.6). Se `competition_awards` i afsnit 2.
Flere turneringer i én konkurrence (`full_season`): turneringsvælgeren i oprettelsen er et multivalg (chips). Vælges flere turneringer, kombineres deres kampe i samme konkurrence (fx "Superliga + Premier League"). Hver chip viser turneringens **kampantal**, og en turnering med nul kampe kan ikke vælges — kampene materialiseres ved oprettelsen, så en tom turnering ville give en konkurrence, der var tom for altid (det var præcis, hvad Champions League gjorde, før tallet blev vist). `full_season` og `team` (flere hold) er multi-turnering; `time_range` er fortsat bundet til én turnering, og `custom`/`random` er allerede liga-løse med turnerings-filter i vælgeren.
Fase-afgrænsning (grundspil/slutspil) findes **ikke** — fjernet 31. juli 2026 sammen med `A20`. En sæson-baseret konkurrence dækker hele sæsonen. Vil man have et slutspil for sig, er det en **ny konkurrence**; det er liga-lagets egen model ("konkurrencer er kapitler i ligaens historie") og billigere end et filter, der skulle holdes i live gennem efterfyldningen. Kampens fase vises stadig som badge på kamprækken (`stageBadgeLabel`, afsnit 7). `mode_params.stages` skrives aldrig længere, men **læses**: findes feltet, er konkurrencen afgrænset i hånden under den gamle ordning og efterfyldes aldrig — se nedenfor.
Efterfyldning af nye kampe (`A20`, 31. juli 2026): kampprogrammer udgives løbende — Champions Leagues knockout trækkes undervejs, Superligaens slutspil skemalægges til foråret. `api/sync-matches.js` føjer derfor nye kampe til de konkurrencer, der allerede findes (`api/backfill.js`), efter kamp-upserten. Tre regler gør det sikkert: **(1)** kun `full_season`, `team` og `time_range` — de er defineret af en regel, der kan genudregnes, mens `custom` og `random` er håndplukkede lister, der aldrig må vokse under fødderne på deltagerne; **(2)** en konkurrence med `mode_params.stages` står urørt (mærkatet ovenfor), så gamle rækker ikke kræver en overgangsregel; **(3)** en **låst runde vokser aldrig** — en kamp tilføjes kun, hvis dens runde endnu ikke er låst, hvilket er strengere end nødvendigt og bevidst: så kan en efterfyldning aldrig udbetale point for et tip, der allerede er afgivet. Låsen regnes pr. `(season_id, round_key)` over hele sæsonens kampe, ikke kun konkurrencens egne. Resultatet aflæses som `backfilled` i jobbets detail-felt (Admin → Drift).
Nye konkurrencer starter altid på 0 point: for `full_season` og `team` (som trækker kampe direkte fra hele sæsonen) udelader oprettelsen automatisk allerede afsluttede runder. Da `predictions` deles på tværs af konkurrencer, ville en ny konkurrence ellers med det samme give point for forudsigelser, man allerede havde afgivet i andre konkurrencer. Reglen: find den første spillerunde (`round_key`) hvor ikke alle kampe har resultat endnu, og medtag kun kampe fra og med den runde (helper: `filterFromNextUnfinishedRound`). Er hele sæsonen allerede spillet færdig, oprettes konkurrencen uden kampe. `custom` og `random` er upåvirket, da de i forvejen kun tilbyder kommende/ikke-spillede kampe i vælgeren; `time_range` filtrerer stadig kun på det datointerval, brugeren selv angiver.
Månedsligaen og sæsonchampionship er særlige "virtuelle" konkurrencer: de findes ikke som `competitions`-rækker, men vises automatisk for alle brugere (se afsnit 5).
Låsen følger kampen, ikke runden og ikke konkurrencen (`A21`, 1. august 2026): en kamp låser 1 time før sit eget kickoff, både i frontenden (`isLocked`/`lockAtOf` i `scoring.js`) og i RLS (`sql/predictions_match_lock.sql`). En runde er derfor typisk **delvist låst i dagevis** — fredagskampen er låst og dens gæt synlige, mens søndagskampen stadig kan tippes. Det er den normale tilstand, ikke en kant.
Hvad der blev fravalgt, og hvorfor: låsen var frem til 1. august scopet på `(season_id, round_key)`, så hele runden låste ved sit tidligste kickoff. En **konkurrence**-scopet lås blev overvejet (`A16`) og er faktisk udtrykbar — aggregerer man over *brugerens egne* konkurrencer, findes der intet hul, fordi deltagelse er frivillig. Den blev fravalgt, fordi deadlinen så ville afhænge af, **hvem du er**: to spillere i samme Rundeliga ville have forskellig frist på samme kamp, og Rundeliga, Månedsliga og Championship er netop de konkurrencer, ingen har valgt. Per kamp er deadlinen derimod en egenskab ved kampen, ens for alle.
Prisen, som er accepteret: den, der tipper søndag, kender fredagens resultater og sin egen stilling. Med `round_wins` som tiebreaker (afsnit 4) og en Rundeliga er det en reel fordel ved at tippe sent — det er præcis den skævhed, juli 2026-beslutningen lukkede, og den er genåbnet med vilje. Der er til gengæld **intet kopierings-hul**: andres gæt for en kamp vises først, når kampen låser, og der kan ingen længere rette sit eget.
Ét sted blev bevidst IKKE oversat mekanisk: `api/backfill.js`' regel 3 ("en runde, der er gået i gang, vokser aldrig") beholder sin runde-betingelse som en selvstændig, strengere efterfyldnings-regel — en per-kamp-udgave ville have gjort den løsere end sin egen begrundelse. Den er efter august 2026 det eneste sted i produktet, hvor runden stadig er et TIDSPUNKT (`analytics_round_locks` har samme grain, men måler kun, om runden er gået i gang).

Det rullende gætte-vindue er fjernet (august 2026, `B1`)
Frem til august 2026 kunne en konkurrence sætte `rules.openDaysBefore` (fast 7 dage, afkrydsning ved oprettelse), så en runde først kunne tippes så mange dage før **rundens første kamp** — scopet `(season_id, round_key)`, altså pr. turnering. Med syv turneringer betød det op til syv åbningstidspunkter i ét rundekort: Champions Leagues midtugekampe åbnede systematisk 3–4 dage før weekendligaernes i samme kalenderuge, og én `full_season` på to turneringer åbnede i to bidder. Vinduet er fjernet frem for omlagt: efter `A21` bæres "alle tipper på samme vidensgrundlag" af per-kamp-låsen, og vinduet var kun en visningsregel i frontenden (aldrig håndhævet af RLS). **Konsekvens:** en kamp kan tippes fra det øjeblik, den findes, og indtil den låser — en `full_season`-konkurrence er dermed tipbar for hele sæsonen fra dag ét. `roundStartKey`/`buildRoundStartMap` er slettet af `scoring.js` med samme begrundelse.

## 4. Pointsystem
+3: præcist resultat (fx gættet 2-1, endte 2-1) — vises i fuld grøn (`C.green` = `#22C55E`)
+1: korrekt udfald (1/X/2), forkert resultat — vises i blød grøn (`C.greenSoft` = `#7fd48a`)
0: forkert gæt, eller ingen forudsigelse afgivet — dæmpet (`C.muted`)
De to grønne nuancer er de samme overalt, hvor point vises: pointpillen (`PointsPill` i `ui/components.jsx`, brugt på Hjem og Tip), facit-boksen på Tip, rundemodalen (`UserRoundPredictions`) og beskrivelsen i "Sådan virker det" → Pointsystem. Farverne bor kun i `ui/theme.js` (`C.green` / `C.greenSoft` / `C.muted`) — hardkod dem ikke igen. På Tip har hver færdigspillet række derfor ÉN grøn: præcist hit = fuld grøn + guldkant, korrekt udfald = blød grøn.
Der er INGEN minuspoint — man kan aldrig gå i minus (de gamle −1/−2 straffe er fjernet). Det handler om at samle så mange rigtige gæt som muligt.
Tiebreaker ved pointlighed — én stige, der gælder ALLE stillinger (konkurrence, rundeliga, månedsliga, sæsonchampionship):
1. flest **præcise resultater**
2. flest **korrekte udfald**
3. flest **rundesejre** (spillerunder hvor man var nr. 1)
4. mindst **målafvigelse pr. tippet kamp** — `sum(|gæt − facit|) / antal kampe`, afrundet til 4 decimaler

Er to spillere lige hele vejen ned, er de **ægte lige**: de deler placering (to delte 2'ere ⇒ næste er nr. 4) og deler en eventuel titel. `user_id` sorteres til sidst som skjult, stabil nøgle, så rækkefølgen ikke driver mellem to hentninger — den afgør aldrig en placering.

Stigen bor ét sted i frontenden (`src/lib/standings.js`: `compareStandings`/`sortStandings`/`assignRanks`/`leaders`) og spejles i SQL af `sql/standings_tiebreakers.sql` (viewenes kolonner `outcome_count`, `round_wins`, `avg_goal_error`), `sql/story_engine.sql` og `sql/career_profile.sql`. Målafvigelsen er et **gennemsnit**, ikke en sum: en sum ville straffe den, der tipper flest kampe, hvilket strider mod beslutning A2. Afrundingen til 4 decimaler sikrer, at SQL og JS er enige om, hvornår to tal er lige.

En **rundesejr** = nr. 1 i den enkelte runde efter samme stige uden trin 3 (point → præcise → udfald → målafvigelse). Delt rundesejr tæller for alle. Rundeligaen ér én runde og springer derfor trin 3 over.
Reglerne er faste og gælder alle konkurrencer (gemt i `rules`-feltet ved oprettelse, med sikre standardværdier — `{ exact: 3, outcome: 1 }` — for ældre konkurrencer uden feltet). Frontenden beregner point i helperen `pointsFor(pred, actual, rules)`.

## 5. Prediction Champ Rating, månedsliga og sæsonchampionship
Rating, månedsliga, rundeliga og sæsonchampionship bor alle i databasen (SQL) og læses af frontenden. SQL-scripterne er idempotente og kan køres igen når som helst (nye scripts ligger i `sql/`-mappen; hele `public`-skemaet er desuden versioneret som øjebliksbillede i `sql/schema.sql` — se afsnit 12).

Prediction Champ Rating
Et selvkorrigerende Elo-tal, der måler hvor gode ens gæt er — ikke hvor mange point man har samlet, og uafhængigt af hvor mange ligaer man er med i.
Princip: hver spillerunde (`round_key`) giver ÉT ratingskridt, på tværs af alle **officielle** ligaer samlet — ikke ét pr. konkurrence og ikke ét pr. kamp. Da `predictions` er én række pr. bruger pr. kamp, tælles hver kamp automatisk kun én gang, uanset hvor mange konkurrencer/ligaer den optræder i.
Omfang (A17, 31. juli 2026): `_rs` joiner `seasons`/`leagues` og tæller kun ligaer med `is_official = true` — samme prædikat som Championships stillinger. En turnering, der kan tippes uden at afgøre titler, flytter altså heller ikke ratingen: "officiel" betyder det samme overalt. **Vilkår, ikke en fejl:** en bruger, hvis tips alle ligger i uofficielle turneringer, får ingen rating-række. Stillingerne viser "–", Hjem skjuler rating-feltet, og Rating-fanens "Hvorfor står jeg her ikke?"-kort nævner turneringen ved navn. Botemidlet er at forfremme turneringen til officiel. Begrundelsen står i `docs/DECISIONS.md`.
Løbende genberegning: rundens skridt beregnes om, hver gang en kamp i runden er fløjtet af — ikke først når runden er slut. `_rs` i `recompute_ratings()` filtrerer kun på "kampen har et resultat" og grupperer på `round_key`; der er bevidst INGEN komplethedsspærre som den, `generate_stories` bruger (kun runder hvor ingen kamp mangler resultat). Da hver genberegning sletter `ratings`/`rating_history` og bygger dem op forfra, bidrager den igangværende runde stadig kun med ét skridt — det regnes blot om efter hver kamp og står endeligt fast, når rundens sidste kamp er spillet. Det, brugeren ser i løbet af ugen, er altså et foreløbigt bud på rundens `delta`.
Beregning pr. runde: hver spiller får en rundescore = point / antal tippede kampe (tiebreak i det parvise opgør: flest præcise — ratingen har bevidst sin egen, enklere regel og bruger ikke stillingernes fulde stige). Alle deltagere sammenlignes én mod én (multiplayer-Elo): man vinder/taber rating alt efter om man gjorde det bedre end forventet ud fra ratingforskellen. At slå en højere ratet spiller giver mere.
Parametre: alle starter på 1000. K = 32 de første 5 runder (foreløbig, markeret med `*` / "NY"-badge), derefter 24. Systemet er nulsum og selvkorrigerende — ingen inflation, ingen sæson-reset nødvendig.
`scope`: `'ALL'` = alle **officielle** ligaer samlet (det eneste der bruges i dag). Kolonnen holder muligheden åben for per-liga-rating senere uden skemaændring — men den mulighed er **bevidst ikke taget** (A17, 31. juli 2026): med én officiel turnering ville en per-liga-Elo have to-tre spillere at være relativ til, altså støj frem for en måling. Rating er ét tal på tværs; det er per-turnering-**stillingen**, der sammenligner æbler med æbler.
Objekter i DB: tabellen `ratings` (aktuel rating), tabellen `rating_history` (snapshot pr. runde, inkl. `delta` = rundens ratingændring), funktionen `recompute_ratings()` (fuld genberegning fra bunden), samt hjælpefunktionen `pc_points(...)`.
Frontend: Rating-fanen viser rangliste + formkurve-prikker (grøn/gul/grå ud fra `delta` for de seneste 5 runder) + bevægelse ▲/▼ (seneste rundes `delta`) + "NY"-badge (foreløbig). Helper: `loadRatingHistory`.

Automatisk genberegning
Tre statement-level triggere på `matches` (`matches_recompute_ratings_ins/_upd/_del`, fra `sql/rating_trigger_optimization.sql`) kalder `recompute_ratings()` automatisk — men KUN når mindst én kamps resultat reelt er ændret, tilføjet eller fjernet (sammenlignet via transition tables). Før kaldte den gamle trigger (`matches_recompute_ratings`) den fulde genberegning ved HVER sætning på `matches`, inkl. cron-syncens upsert hvert 10.-15. minut uden ændringer. Statement-level betyder stadig én kørsel pr. sætning, også når en hel runde gemmes på én gang.
Der er også en manuel "Opdater ratings"-knap i Admin-skærmen (kun admin, nås via tandhjulet i topbjælken) som reserve.
Da `api/sync-live.js` færdigmelder en kamp inden for et minut efter slutfløjt (afsnit 10), rykker rating i praksis efter hver enkelt kamp. Konsekvenser midt i en runde, som er forventede og ikke fejl: `round_score = pts/n` svinger kraftigt, når `n` kun er 1-2 kampe; modstanderfeltet er kun de spillere, der har mindst én afgjort kamp i runden, så puljen kan være lille og skæv tidligt på ugen; og `rounds_played`/`provisional` tæller den igangværende runde med, så "NY"-badget kan falde væk allerede ved rundens første afgjorte kamp.

Rundeliga
Alle brugere er automatisk med. Samlede point for én enkelt spillerunde (`round_key`), hver kamp én gang. **To niveauer** (`sql/tournament_scope.sql`, 31. juli 2026): `scope = 'ALL'` samler alle **officielle** turneringer og kårer *Rundens Prediction Champ*; `scope = <league_id>` giver én stilling pr. officiel turnering med kåringen *"Rundens bedste i X"*. Kun det samlede bærer ordet "Prediction Champ" — rangordenen ligger i navnet. Rangeres efter flest point med tiebreaker-stigen fra afsnit 4 (dog uden rundesejr-trinnet — det ér én runde); den øverste kåres som Rundens Prediction Champ, når runden er færdigspillet, og titlen deles ved ægte lighed. Stillingen beregnes i DB-viewet `round_standings` (`sql/standings_tiebreakers.sql`) og læses af `loadRoundBoard(token, roundKey)`; `loadRoundsAvailable(token)` giver de runder, der har mindst én spillet kamp (nyeste først, valgbar i en dropdown). Championship-fanen lander på den seneste runde. Begge tager `scope` som sidste argument (default `'ALL'`). **Kampantallet følger samme afgrænsning som pointene** — `scopeSeasonIds()` slår sæsonerne op under de officielle turneringer (eller under den ene valgte): antallet afgør `isComplete` og dermed, om pokalen og titlen vises, så en turnering uden for stillingen ville ellers holde runden åben, indtil kampe, ingen konkurrerer om, var spillet. Grænsen: selve pointene kommer fra viewet og kan ikke filtreres fra klienten — fjernes en turnerings officielle status, *efter* der er tippet på den, forsvinder dens tips fra stillingen ved næste opslag, men historiske `stories` og karrieretal er skrevet ud fra den gamle afgrænsning. Kun spillede/låste kampe indgår i viewet, så RLS tillader at læse alles gæt.

Månedsliga
Alle brugere er automatisk med — ingen tilmelding. Viewet `monthly_standings` summerer hver brugers point for alle kampe i en kalendermåned (igen: hver kamp én gang), på **samme to niveauer som rundeligaen** — `scope`-kolonnen fandtes i forvejen, hårdkodet til `'ALL'`, og blev udvidet med per-turnering-rækker. Rangeres efter flest samlede point med hele tiebreaker-stigen fra afsnit 4; den øverste er Månedens Prediction Champ (titlen deles ved ægte lighed). Stillingen nulstilles reelt den 1., fordi viewet grupperer på måned. Tidligere måneder kan vælges i en dropdown og ligger fast, da kampene er spillet. Helper: `loadMonthlyBoard`.

Sæsonchampionship
Alle brugere er automatisk med. Samlede point for alle kampe i en ligas aktuelle sæson (i praksis Superligaen), rangeret efter flest point med hele tiebreaker-stigen fra afsnit 4; den øverste er Sæsonens Prediction Champ (titlen deles ved ægte lighed). Stillingen beregnes i DB-viewet `season_standings` (`sql/standings_tiebreakers.sql`) og læses af `loadSeasonBoard(token, leagueId)`, som derudover kun henter sæsonens kampe til fremdrifts-tælleren (spillet/total). Kun spillede kampe indgår i viewet, og de er altid låste, så RLS tillader at læse alles gæt (ingen snyde-risiko). **Én sæsonstilling pr. turnering:** er der mere end én synlig turnering, vælges den i en dropdown på kortet; med kun én vises ingen vælger. Forvalget kommer fra `pickSeasonLeague()` i `src/screens/ChampionshipTab.jsx` — brugerens eget valg (husket i `localStorage`), ellers den **ældste** turnering (`created_at`). Bevidst ikke navnesorteret: listen ér sorteret på navn, så alfabetet ville sætte "Scotland Premiership" foran "Superligaen". *(Erstattede 31. juli 2026 navne-regexet `/superliga/i` — se `docs/features/turnering-2.md` §3.2.)* En samlet sæsonstilling på tværs af turneringer er fravalgt; den rolle har månedsligaen og ratingen. **Bevidst undtagelse fra navneregelen** (31. juli 2026): sæsonkåringen hedder fortsat "Sæsonens Prediction Champ", selvom den er pr. turnering — reglen om, at kun det samlede bærer titlen, gælder dér, hvor to niveauer konkurrerer om samme navn, og en sæson er turneringsbunden af natur. Kortet viser kun **officielle** turneringer.

Rettigheder: `ratings` og `rating_history` har RLS med læse-adgang for `authenticated`. `recompute_ratings()` er `security definer` (kører som ejer). `round_standings` og `season_standings` er `security_invoker` og arver dermed `predictions`/`matches`' adgang. `monthly_standings` har **bevidst IKKE** `security_invoker` (`sql/standings_tiebreakers.sql` afsnit-kommentaren): tiebreaker-migreringen ændrede kun kolonner, ikke adgangsregler. Kun kampe MED resultat indgår i alle tre views, og de er altid låste, så alles gæt må læses (ingen snyde-risiko).

## 6. Unikke brugernavne
`profiles.display_name` har et unikt, case-insensitivt indeks (`profiles_display_name_lower_idx`) — den egentlige garanti mod dubletter, også ved samtidige oprettelser.
Funktionen `username_available(name)` (kaldbar af `anon` + `authenticated`) tjekker om et navn er ledigt, før kontoen oprettes. Frontenden kalder den ved signup og blokerer med en venlig besked ("Brugernavnet er allerede taget"), så man ikke får oprettet en konto der alligevel fejler.
Et brugernavn behøver ikke være ens rigtige navn; Hjem-fanen hilser med hele `display_name`.
Længde: **2–20 tegn**. Håndhæves i frontenden (`Auth.jsx`) og af en check-constraint på `profiles.display_name` (`sql/username_constraints.sql`, `NOT VALID` så gamle rækker ikke fejler). Grænsen beskytter mobil-layoutet, da `display_name` bl.a. bruges som kolonneoverskrift i "Point pr. runde"-tabellen.

## 7. Brugerflade og navigation
Appen er mobil-first med en bundnavigation på fem faner og en topbjælke.

Topbjælke: krone + "Prediction Champ", samt til højre: profil-ikon (→ egen karriereprofil, afsnit 19), ⓘ (åbner "Sådan virker det"-siden), tandhjul (kun admin → Admin-skærmen), og log ud.

De fem faner (bundnav):
Hjem — deadline-kort (næste rundes deadline + antal kampe der mangler tips + "Tip nu"-knap; helper `computeHomeTips`), rating-snapshot ved siden af brugernavnet (kun tal + `*` ved foreløbig + bevægelse ▲/▼ — placering og formkurve er bevidst udeladt for at spare plads; et tryk åbner **karriereprofilen**, ikke Rating-fanen), og "Dine placeringer" (månedsliga øverst, dernæst konkurrence-placeringer grupperet pr. liga (liga-laget, afsnit 18) — liga-løse under "Øvrige"; har man ingen ligaer, vises de fladt; hver linker videre). Tips-status har **fem** gensidigt udelukkende tilstande, som `computeHomeTips` afgør: rødt "Runde X · N kampe mangler tips" (`allTipped === false`), grønt "Alt ok — alle tips er inde" (`allTipped`), "Intet at tippe lige nu" (`nothingToTip` — alle kampe i brugerens konkurrencer er låst eller spillet), "ingen kampe endnu" (`noMatches`) og en fejltekst (`error`). Skelnen mellem de to første og `nothingToTip` er vigtig: "alle tips er inde" er en påstand om BRUGERENS tips og blev før også vist, når der bare ikke var noget tipbart — så en bruger med nul tips fik grønt kort. `noMatches` og `error` havde tidligere slet intet kort. Tom-tilstanden er erstattet af **"Kom godt i gang"-kortet** (`GetStartedCard.jsx`, afsnit 20): de to tidligere dashed kort sagde hver især én ting ("du har ingen liga" / "du har ingen konkurrence"), mens checklisten viser hele vejen på én gang — liga, konkurrence, første tip, invitér en ven — og forsvinder af sig selv, når alt er klaret. `HjemTab` henter derfor ikke længere selv `loadMyGroups`; tilstanden kommer som prop fra `MainApp`. Derunder en live-oversigt over indeværende runde (resultat/tip/point pr. kamp + samlede point), der genindlæses hvert minut mens kampene spilles (helper `computeCurrentRound`). Kampe i gang vises med den nuværende stilling + LIVE-mærke (afsnit 8) — også på det foldede kort — mens færdigspillede kampe vises med resultat + point-pille. Nederst et opt-in-kort til push-notifikationer (afsnit 16), som kan skjules og forsvinder når man er tilmeldt — det vises kun, når checklisten IKKE står, da notifikationer dér er en af dens rækker; begge bruger `usePushOptIn`, så der kun findes én definition af, hvornår spørgsmålet giver mening.
Tip — se drill-in-beskrivelsen nedenfor; skærmen er både en fast fane (ufiltreret) og en drill-in, når den åbnes filtreret fra Stilling eller fra Hjem-kortenes knapper.
Ligaer — liga-laget (afsnit 18), oppefra: opret/deltag, dernæst brugerens **liga-kort** (navn, antal medlemmer og konkurrencer → liga-siden). Opret/deltag har to tilstande (A22/`I4`): har man **ingen** ligaer, vises to fulde kort — "Opret en liga" (navnefelt, 2–40 tegn) og "Deltag med kode" (tager BÅDE liga- og konkurrence-koder) — for dér ER de opgaven; har man ligaer, er de foldet sammen til én kompakt knap-række ("+ Opret liga" · "Deltag med kode"), der folder det respektive inputfelt ud ved klik, så ligalisten er det første, man ser. Derunder afsnittet "Øvrige konkurrencer" med de liga-løse konkurrencer, som virker som før: kort med navn, type (`modeLabel`), deltagere, fremdrift og egen placering (ægte rang — delt placering siges "delt plads"), samt "Ny"-knap, Arkivér/Gendan (kun afsluttede/arkiverede), Slet (kun opretteren) og en engangs-opfordring til at samle dem i en liga. Klik på et konkurrence-kort → Stilling.
Championship — officielle konkurrencer, alle automatisk med: Rundeliga (rundevælger + Rundens Prediction Champ), Månedsliga (månedsvælger + Månedens Prediction Champ) og Sæsonchampionship (live stilling + Sæsonens Prediction Champ + progress). Hvert kort viser **top 5** i samme tabelformat som konkurrence-stillingen (#, Spiller, Rating, 🎯, Point); "Vis hele stillingen (N)" åbner en modal med paginering (maks. 20 pr. side). Kåringsbanneret navngiver **alle** på 1. pladsen ved ægte lighed ("er delt Månedens Prediction Champ"), og siger "fører lige nu", indtil perioden er afsluttet. Nederst et stiplet pladsholder-kort til fremtidige events.
Rating — rangliste med rating, formkurve-prikker (seneste 5 runder), bevægelse ▲/▼ og "NY"-badge. Egen række fremhæves. Placeringen sættes af `assignRanks` med en **rating-komparator** (`loadRatingBoard`), så to spillere med samme viste rating deler nummer.

Drill-in-skærme (nås fra fanerne, ikke i bundnav):
Stilling — vælg konkurrence i dropdown; viser placering (ægte rang — to lige spillere får samme nummer, og forklaringslinjen siger "ens placering = delt"), Rating (`*` = foreløbig), 🎯 (præcise resultater), Form (point i seneste 3 runder) og ▲/▼ for placeringsændring. **Hele rækken** er tryk-fladen for spillerens forudsigelser runde for runde (bladr frem/tilbage); **navnet** ligger ovenpå, stopper propagationen og åbner i stedet karriereprofilen (`PlayerName`). Et pointtal i "Point pr. runde"-tabellen åbner samme visning landet på netop den runde. **Snyde-sikring: kampe vises fra deres LÅS** (`lockedRoundsOf` i `scoring.js`), ikke fra færdigspillet runde — fra låsen kan ingen rette sit gæt, så der er intet at beskytte. Hver runde beskæres til sine låste kampe; efter `A21` vokser en runde her løbende, fordi kampene låser én ad gangen. En låst, endnu ikke spillet kamp viser gættet med "–" som facit og ingen point. "Invitér"-knap deler altid **konkurrence**-linket (`?join=kode`) — også for konkurrencer i en liga, hvor modtageren samtidig meldes ind i ligaen (A7/A8, afsnit 18). Liga-linket deles fra liga-siden. "Point pr. runde"-tabel: spillere som kolonner, runder som rækker, nyeste øverst, kun de 3 seneste vises med en "Vis alle X runder"-knap. Har konkurrencen tilvalgt kåringer (`mode_params.awards`, A22/afsnit 3), står en **"Kåringer"-sektion** mellem stillingen og rundetabellen: åbningen trigger `award_competition_periods()` (lazy, idempotent) og viser "🏅 Ugens bedste · <runde>: <navn> (<point>)" og "Månedens bedste · <måned>: …", delte sejre markeret "delt".
Tip (forudsigelser) — filtrér på liga (matchens egen liga via `season_id`) og/eller konkurrence ("Alle konkurrencer" eller én). Filtrene er chip-formede dropdowns, der **kun vises, når der er noget at vælge** (>1 turnering / >1 konkurrence) eller når et filter faktisk er sat (Tip kan åbnes filtreret fra stillingen); et aktivt filter er grønt og viser navnet. Kampe deduplikeres pr. runde. Starter på den runde der indeholder i dag (eller nærmeste kommende). Grønt ✓ efter et gemt gæt.
Rundehoved: rundelabel + pager (`x/y`) på én linje, og rundens tilstand på én dæmpet linje under — fire gensidigt udelukkende tilstande: `Spillet · N point` / `Låst · N af M tippet` / `N af M tippet · Låser om X t Y min` (én kamp tilbage) / `N af M tippet · Næste lås om …` (flere). Logikken bor i `screens/predictions/roundStatus.js`. Låsen er per kamp (`A21`), så hovedet siger kun, hvornår den FØRSTE af de tipbare kampe løber ud; hver kamprække viser sit eget kickoff i tid-kolonnen og bærer ingen nedtælling. Deadline vises som relativ nedtælling under et døgn, absolut tid derover.
Kampene er grupperet pr. kampdag med en dag-overskrift ("LØR 25. JUL"), så rækken kun viser klokkeslættet.
**Låst = en tabel.** Hver låst kamp er **én linje** i et fast grid (`ROW_COLS` = tid 36 · navn `1fr` · gæt 25 · facit 38 · point 26 · chevron 14, `gap` 4), og har en kampdag mindst én låst kamp, står der ét kolonnehoved (`Gæt · Facit · P`) over netop den dags rækker. Hovedet stod før én gang for hele runden, hvilket forudsatte, at runden var enten låst eller åben; efter `A21` er en runde blandet i dagevis, og hovedet hører derfor til DAGEN — 1-times-vinduet er kort nok til, at en kampdag i praksis er enten forbi eller fremme. Kolonnerne er det, der gør de tre tal entydige — før stod de uden overskrifter og skulle læses udenad. Tid-kolonnen bærer kampens tilstand: `Slut` (færdigspillet), pulserende prik + spilleminut eller `Pause` (i gang), ellers klokkeslættet. Facit står i farvet ramme (guldkant ved præcist hit), live-stillingen i neutral rød-kantet ramme uden point (de afgøres først ved slutfløjt), og pointpillen kun når kampen er tippet. Er hele runden spillet, udelades `Slut` (hovedet siger det).
**Hele den låste række er tryk-fladen for "alles gæt"** — en rigtig `<button>` med `aria-expanded`, ~340 × 42 px, med et guldfarvet chevron som synligt tegn. Det er sikkert netop her, fordi en låst række ikke har indtastningsfelter (`canExpand = locked`), og det er samme mønster som stillingsrækken i `BoardScreen`. Forklaringslinjen "Tryk på en kamp for at se alles gæt" står **én gang** i rundehovedet (kun når runden er låst og der er mere end én deltager) i stedet for en "Alles gæt"-knap på hver eneste række — det var den linje, der fordoblede rundens højde.
**Holdnavnene sættes i `font.display` (Barlow Condensed)**, som fylder ~25 % mindre end brødskriften. `TeamNames` måler i en `useLayoutEffect` og falder ét trin ad gangen (15 → 13,5 → 12,5 px), hvis navnet ikke kan være der; først når trinene er brugt op, ombrydes der. Der trunkeres **aldrig** — et afkortet holdnavn er skjult information. Målt i Chromium: fra 375 px og opefter står alle kampe på én linje, også sæsonens længste par (`Lyngby Boldklub – FC Nordsjælland`); ved 360 px ombryder de to længste. Målingen kræver, at Barlow Condensed faktisk er indlæst — sker den mod fallback-skriften, er resultatet ~25 % for pessimistisk.
**Åben runde** beholder sin flex-form med to `ScoreInput`-felter og grønt ✓, og får hverken kolonnehoved eller chevron: der findes hverken facit, point eller andres gæt at vise endnu.
**Linje 2 er nu undtagelsen**, ikke reglen: den renderes kun til stage-mærket og en slettefejl. LIVE, Slut og "Alles gæt" er flyttet ind i selve rækken, og "Åbner …" forsvandt med det rullende vindue (afsnit 3).
Er der mere end én kamp tilbage at tippe, siger hovedet "Næste lås om …" i stedet for "Låser om …" — efter `A21` har hver kamp sin egen deadline, så tiden i hovedet gælder den første, der løber ud. Rækkerne bærer **ingen** nedtælling: lås = kickoff − 1 time, og rækkens tid-kolonne viser allerede kickoff, så deadlinen er aflæselig af det, der står i forvejen. Det er derfor, per-kamp-låsen ikke kostede den kompaktering, tabelvisningen gav. Statuslinjens fem tilstande bor i `predictions/roundStatus.js` som ren funktion og er unit-testet.
"Alles gæt" foldes ud under en låst kamp og viser alle deltageres gæt + point.
`MatchRow`, `RoundHeader` og `TeamNames` er navngivne eksporter fra `PredictionsScreen.jsx`, så de kan renderes isoleret i test (`PredictionsScreen.test.jsx`) og måles i en rigtig browser.
Opret konkurrence (`CreateCompetitionScreen.jsx`) — galleri-først (A22, afsnit 3; spec: `docs/features/opret-flow-v2.md`): trin 1 er "Hvad vil I spille?" med seks kort (Sæson, Favorithold, Quick League, Quick Pick, Ugens kupon, Custom — rækkefølgen langt → kort, og det øverste kort bærer mærket "Anbefalet"; hvert kort har et ikon og en varigheds-mærkat, fordi typerne adskiller sig på to akser: hvilke kampe og hvor længe), trin 2 kun den valgte types egne felter plus de fælles: navn (tomt — kun Ugens kupon forudfylder sit genererede navn), **liga-dropdown** (hvilken liga konkurrencen skal ligge i, eller "Ingen liga" — aldrig skjult), og kårings-tilvalget (kun flerrunde-typer). Skærmen er en tynd container: typekataloget og spec-bygningen bor i `src/lib/createTypes.js`, felterne pr. type i `src/screens/create/`, skrivningen i `data/competitions.js` (delt med onboarding-guiden). Mode-navnene kommer fra `MODE_LABELS` i `scoring.js`, så opret-skærmen, Ligaer-kortet, liga-siden og admin-statistikken kalder den samme mode det samme — `modeLabel(mode, mode_params)` skelner Quick League fra Quick Pick på `rounds`-feltet (admin-statistikken aggregerer uden params og viser derfor Quick League som Quick Pick — accepteret).
Karriere (`ProfileScreen.jsx`) — brugerens karriere: hoved, titler, milepæle (kun egen), ratingkurve, rivaler (kun egen) og basistal. Nås fra ethvert brugernavn i appen og fra profil-ikonet i topbjælken. Se afsnit 19.

## 8. Automatisk resultathentning (`api/sync-matches.js`)
**Datakilden er ligaens, ikke kodens.** `leagues.provider` afgør, hvem der spørges (registret: `api/providers/index.js`, spec: `docs/features/flere-datakilder-v1.md`). To leverandører er i drift, fordi ingen af deres gratis-planer dækker det hele: **Sportmonks** har Superligaen og Scotland Premiership; **football-data.org** har Premier League, Champions League, Bundesliga, Serie A og Primera División. Providermodulet ejer alt leverandørspecifikt (URL, auth, paginering, feltnavne) og returnerer en normaliseret kamp; resten af syncen — holdmatchning, upsert, job-logning — er fælles og kender ingen leverandørs feltnavne.
**Id-præfiks:** `matches.api_fixture_id` har en global unique-constraint, og begge leverandører bruger almindelige heltal. football-data.org-id'er gemmes derfor som `fd:537654`, mens Sportmonks beholder bare tal (deres id'er står allerede i basen). Samme konvention på `teams.api_team_id`. Konventionen ejes af `toGlobalId()`/`fromGlobalId()` i providermodulet — ikke af kaldstederne.
Slår ligaens liga-id hos leverandøren og gemte sæson-id op (eller sæson-navn første gang, og gemmer id'et)
Henter alle kampe for sæsonen. Sportmonks pagineres (~4 kald pr. kørsel); football-data.org returnerer hele sæsonen i ÉT kald. Hver kamps stage gemmes i `matches.stage_name` — grundspil/mesterskabsspil/nedrykningsspil, og for CL desuden ligafase/ottendedelsfinale/… Superligaen er én sæson med flere stages, så alle stages hentes i samme kald
Auto-opdager og opretter hold ud fra kampenes deltagere
Udtrækker resultat kun når leverandøren melder slut (Sportmonks: `state.short_name` = `FT`/`AET`/`FT_PEN`, scoren fra `description: "CURRENT"` · football-data.org: `status` = `FINISHED`/`AWARDED`, scoren fra `score.fullTime`)
Springer kampe uden begge hold over og tæller dem i `undrawn` i svaret. Hos Sportmonks er det en datafejl; i Champions League er det normalt — knockout-kampene findes i kampprogrammet før lodtrækningen og har da ingen hold. Står `undrawn` stille hen over en lodtrækning, henter syncen ikke de nye kampe
Upserter kampene i Supabase (`api_fixture_id` er unik nøgle)
Bemærk: når sync opdaterer kampe med resultat, udløser DB-triggeren automatisk en rating-genberegning (afsnit 5)
Kaldes med: `/api/sync-matches?leagueId=<uuid>&smSeason=2026/2027`
Test uden at skrive noget: tilføj `&dryRun=true`
Adgang: enten en admin-brugers login-token (bruges automatisk af "Hent resultater nu"), eller den delte `SYNC_SECRET`. Hemmeligheden sendes helst i headeren `x-sync-secret` (så den ikke havner i request-logs); `&secret=<SYNC_SECRET>` i query-strengen virker fortsat som fallback. Flyt gerne cron-job.org-jobbet til headeren.
Automatisk kørsel: cron-job.org kalder linket hvert 10.-15. minut (Vercels gratis cron er kun 1×/døgn, for sjældent). Ét cron-job pr. liga.

Live-resultater (`api/sync-live.js`)
Formål: mens en kamp spilles, vises den nuværende stilling i appen ("2-1 · LIVE 63′") i stedet for blot "I gang". Tabeller og rating rører sig først ved slutfløjt.
Grundprincippet: live-scoren skrives i SEPARATE kolonner (`matches.live_home_score`, `live_away_score`, `live_state`, `live_minute`, `live_updated_at` — `sql/live_scores.sql`) og rører ALDRIG `home_score`/`away_score`. Hele appen bruger "`home_score is not null`" som betydningen "kampen er spillet færdig": pointberegning (`pointsFor`), stillings-views (`round_standings`/`season_standings`/`monthly_standings`), rating-triggeren, låsningen (`isLocked`) og Story Engine. Skrev vi live-scoren i `home_score`, ville stillinger begynde at give point midt i en kamp, og rating-triggeren ville køre en fuld Elo-genberegning hvert minut. Med separate kolonner er alle de veje uændrede — triggeren (`sql/rating_trigger_optimization.sql`) sammenligner kun `home_score`/`away_score` og reagerer derfor slet ikke på live-opdateringer.
Sådan virker kørslen (hvert minut):
1. Finder i vores egen database de kampe, der kan være i gang: uden endeligt resultat med kickoff i vinduet [nu − 6 t; nu + 15 min], plus alle kampe der stadig står markeret som live (så en hængende markering altid ryddes).
2. Er der ingen — hvilket er de fleste minutter i døgnet — returneres med det samme UDEN at kalde nogen datakilde. Det holder forbruget nede på gratis-planerne. De to liga-/sæson-opslag i trin 3 ligger bevidst EFTER denne retur.
3. Ellers grupperes kampene efter deres ligas datakilde (`matches.season_id` → `seasons.league_id` → `leagues.provider`; der er med vilje INGEN provider-kolonne på `matches`, som ville kunne komme i utakt med ligaens). Hver leverandør spørges for sig: Sportmonks henter præcis de kampe i ét kald pr. 40 (`fixtures/multi/{ids}?include=scores;state;periods`); football-data.org henter ét datovindue, som dækker alle dens turneringer på én gang. Ét job dækker ALLE ligaer og begge leverandører (modsat `sync-matches`, der er ét job pr. liga). **Fejler én leverandør, skrives de øvriges opdateringer alligevel**, og kørslen ender derefter som fejlet — en manglende football-data-nøgle må ikke kunne stoppe Superligaens live-scores.
4. Pr. kamp: melder leverandøren slut, skrives det **endelige** resultat (`home_score`/`away_score`, `status='finished'`) og live-felterne ryddes — det er her point, stillinger og rating bevæger sig. Er kampen i gang, skrives kun live-felterne. Er den hverken i gang eller færdig (ikke startet, udsat, aflyst), ryddes live-felterne.
   **`leagues.live_enabled = false` ⇒ live-felterne skrives ALDRIG for ligaen, kun endelige resultater.** Sådan står de fem football-data.org-turneringer, hvis gratis-plan har forsinket stilling og intet spilleminut. Kampe, der er i gang, men undertrykt, tælles i `liveSuppressed` i kørslens svar — tallet er den synlige kvittering for, hvad €12/md-planen ville købe. Tegnes den, er opgraderingen én `update` (se `sql/multi_provider.sql`), ikke en kodeændring.
5. Alle ændringer skrives i ÉN upsert (`on_conflict=api_fixture_id`), så statement-triggeren på `matches` kører netop én gang pr. kørsel.
Sidegevinst: kampe færdigmeldes nu inden for et minut efter slutfløjt i stedet for at vente op til 15 minutter på næste `sync-matches`-kørsel.
Adgang: samme som `sync-matches` (`x-sync-secret`-header, `?secret=` som fallback, eller en admin-brugers token). Test uden at skrive: `&dryRun=true`.
Opsætning: ÉT cron-job på cron-job.org, hvert minut, mod `https://<app>/api/sync-live` med headeren `x-sync-secret`. Ingen query-parametre — funktionen finder selv de relevante kampe på tværs af alle ligaer. **Udførlig trin-for-trin-guide (inkl. test, verifikation og fejlfinding): `docs/features/live-resultater-v1.md` afsnit 7.** `sync-matches`-jobbene (ét pr. liga) bevares, men kan skrues ned til hver 6. time: de skal kun holde kampprogram, flyttede kampe og nye hold ajour, for resultaterne kommer nu fra live-syncen.
Sportmonks-forbrug (gratis-planen = 180 kald i timen pr. entitet): `sync-live` bruger ét kald pr. minut, men KUN mens kampe er i vinduet — maks. 60 kald/time på en kampdag, nul resten af tiden. `sync-matches` er den dyre (hele sæsonen med paginering, ~4 kald pr. kørsel pr. liga); derfor anbefalingen om at skrue den ned.
football-data.org-forbrug (gratis-planen = **10 kald/minut**, en rate limit — ikke en månedspulje): `sync-matches` bruger **ét** kald pr. turnering pr. kørsel, altså 5 kald pr. døgn ved to kørsler i døgnet · 5 turneringer = 10 kald/døgn. `sync-live` bruger ét kald pr. minut, som dækker ALLE fem turneringer på én gang, og kun mens kampe er i vinduet. Værste minut er derfor 5 `sync-matches`-jobs + `sync-live` = **6 af 10**, og cron-jobbene spredes alligevel på forskellige minutter. Ved 429 prøver providermodulet igen én gang efter `X-RequestCounter-Reset` — sker det, er det et tegn på, at jobbene er faldet sammen på samme minut, ikke at loftet er for lavt.
Engangsopsætning i databasen: kør `sql/live_scores.sql` i Supabase ("Run without RLS"). Ingen ny RLS-policy er nødvendig — `read matches` giver allerede alle authenticated læseadgang til alle kolonner.
Frontend: helperen `liveInfo(match)` i `src/lib/scoring.js` er det ene sted, der oversætter live-kolonnerne til UI-tilstand (returnerer `null`, hvis kampen ikke er i gang — et endeligt resultat slår altid live). Vises som rødt, pulserende `LiveBadge` (Hjem-fanens runde-oversigt og Tip-skærmen); en færdigspillet kamp får et dæmpet `FinalBadge` ("Slut"). Hjem-kortet genindlæser i forvejen hvert minut; Tip-skærmen genhenter kun kampene, når mindst én kamp er i live-vinduet.

## 9. Miljøvariabler
Variabel	Formål
`SPORTMONKS_TOKEN`	API-nøgle til Sportmonks. Kræves kun af ligaer med `provider = 'sportmonks'`
`FOOTBALLDATA_TOKEN`	API-nøgle til football-data.org (sendes som headeren `X-Auth-Token`). Kræves kun af ligaer med `provider = 'footballdata'`
`SUPABASE_URL`	Supabase-projektets URL
`SUPABASE_SERVICE_ROLE_KEY`	Server-side Supabase-nøgle (aldrig i frontend)
`SYNC_SECRET`	Autoriserer eksterne cron-kald til serverfunktionerne
`VAPID_PUBLIC_KEY`	Web Push: offentlig VAPID-nøgle (generér med `npx web-push generate-vapid-keys`)
`VAPID_PRIVATE_KEY`	Web Push: privat VAPID-nøgle (aldrig i frontend eller git)
`VAPID_SUBJECT`	Valgfri `mailto:`-kontaktadresse, som sendes til push-tjenesterne
Disse bruges kun af serverfunktionerne (`api/sync-matches.js`, `api/sync-live.js` og `api/send-notifications.js`). Alle tre kræver `SUPABASE_URL`, `SUPABASE_SERVICE_ROLE_KEY` og `SYNC_SECRET`; API-nøglerne hentes derimod først, når en liga faktisk skal synkroniseres, og kun leverandørens egen (`providerToken()` i `api/providers/index.js`). Det er ikke en detalje: et hårdt krav om `SPORTMONKS_TOKEN` ved opstart ville blokere en football-data-liga, der aldrig bruger den. Mangler nøglen, nævner fejlen variablen ved navn. Frontenden bruger som udgangspunkt en hårdkodet offentlig `SUPABASE_URL` + `publishable`-nøgle (i `src/lib/supabase.js`), men kan pege på en anden database via to valgfrie byggetids-variabler:
`VITE_SUPABASE_URL`	Frontend: overstyr Supabase-URL (fx staging). Udeladt = produktion

## 10. Sådan tilføjer du en ny turnering
**Vælg først datakilde.** Turneringen skal være i én af de to gratis-planer, ellers er der ikke noget at hente: **Sportmonks** har Superligaen + Scotland Premiership (`provider = 'sportmonks'`), **football-data.org** har 12 turneringer, heriblandt Premier League, Champions League, Bundesliga, Serie A, Primera División, Eredivisie, Primeira Liga, Championship, Brasileirão, VM og EM (`provider = 'footballdata'`). Er den i begge, vælg Sportmonks: kun den leverer livescore på gratis-planen.
Find ligaens id hos leverandøren — og verificér, at den er i planen. Sportmonks: `GET /v3/football/leagues?api_token=…` returnerer netop planens turneringer; en turnering uden for den er ikke bare "ikke synlig", syncen fejler. football-data.org: `curl -H "X-Auth-Token: $T" https://api.football-data.org/v4/competitions` — id'et er den korte **kode** (`PL`, `CL`, `BL1`, `SA`, `PD`), og en turnering uden for planen svarer 403.
Slå sæsonen op. Sportmonks: `GET /v3/football/leagues/<id>?include=seasons` — navnet skal matche nøjagtigt i næste trin. football-data.org: der er intet sæson-id at slå op, `?season=` tager **startåret** (`2026`).
Indsæt en ny række i `leagues` (+ `api_league_id`, **`provider`**, **`live_enabled`**, `is_visible`, **`is_official`**) og en sæson-række i `seasons`. **`live_enabled` følger abonnementet, ikke leverandøren:** `false` på football-data.orgs gratis-plan (forsinket stilling, intet spilleminut), `true` hos Sportmonks. **`is_official` er et selvstændigt valg:** den afgør, om turneringen fodrer Championship (runde-/måneds-/sæsonkåringerne) og dermed ændrer, hvad en titel betyder. Nye turneringer bør begynde som `is_official = false` og forfremmes bevidst — `is_visible` styrer kun, om nogen kan se og tippe den. En officiel turnering SKAL være synlig (check-constraint). **Sæt `api_season_id` med det samme** (id'et står som "Current Season ID" på Sportmonks' ligaside): så er første sync et almindeligt kald, og Admin-knappen "Hent nu" virker fra første klik. Skabeloner: `sql/tournament_scotland_premiership.sql` (Sportmonks) og `sql/tournament_footballdata.sql` (football-data.org).
Kald sync-funktionen: `/api/sync-matches?leagueId=<uuid>` (`&dryRun=true` først). **`leagueId` er vores egen `leagues.id`-uuid — ikke Sportmonks' id**, som står i `api_league_id`. Den opretter selv holdene. Er `api_season_id` IKKE sat, skal første kald i stedet have `&smSeason=<sæsonnavn>` — navnet skal matche Sportmonks nøjagtigt, id'et slås så op og gemmes. Admin-knappen sender ikke `&smSeason=`, så netop dét kald skal ske via URL.
**Kaldet SKAL autoriseres, og det kan en adresselinje ikke.** `isAuthorized()` (`api/_shared.js`) kræver enten sync-hemmeligheden eller et admin-login som `Authorization: Bearer <supabase-JWT>`. Appens session ligger i `localStorage` og ikke i en cookie, så det hjælper ikke at være logget ind i browseren — en almindelig navigation sender ingen af delene og får `{"error":"Ikke autoriseret"}` (401). Der er tre veje ind, og de har hver sin pris:
**1) `curl` med hemmeligheden — den eneste, der kan køre `dryRun` uden bøvl.** Kræver `SYNC_SECRET` fra Vercels miljøvariabler.
```bash
curl -s -H "x-sync-secret: $SYNC_SECRET" "https://<app>/api/sync-matches?leagueId=<uuid>&dryRun=true"
```
Alt på ÉN linje, og hele URL'en i anførselstegn — `&` skiller ellers kommandoen. På Windows `cmd.exe` gælder desuden, at `\` ikke er linjefortsættelse (det er `^`), og i PowerShell skal der stå `curl.exe`, da `curl` dér er et alias for `Invoke-WebRequest` med helt andre argumenter.
**2) Admin → Kampe → "Hent nu" — ingen hemmelighed, intet token.** Knappen sender admin-brugerens eget JWT. Den kan til gengæld **ikke** køre `dryRun` og sender ikke `&smSeason=`, så den forudsætter, at `api_season_id` allerede står på sæson-rækken.
**3) Devtools-konsollen med et kopieret token** — når man vil have `dryRun` uden at kende hemmeligheden. **Tokenet kan IKKE hentes fra `localStorage`:** `pc_session` indeholder kun `refresh_token` og `user` (`App.jsx`, `saveSession`), mens adgangstokenet kun lever i React-state. `s.access_token` er `undefined` og giver `Bearer undefined` → 401. Kopiér det i stedet fra et kald, appen selv laver: F12 → **Network** → et vilkårligt kald til `…supabase.co/rest/v1/…` → **Request Headers** → `authorization: Bearer eyJ…`.
```js
fetch("/api/sync-matches?leagueId=<uuid>&dryRun=true", { headers: { Authorization: "Bearer eyJ…" } })
  .then((r) => r.json()).then(console.log);
```
`?secret=<SYNC_SECRET>` i adresselinjen virker også, men **undgå det til manuelle kald**: hemmeligheden havner i browserhistorik og request-logs, og kaldet udløser `[A11]`-advarslen i Vercels logs — netop det signal, hvis fravær `A11` venter på for at kunne fjerne fallbacken (`docs/CRON.md`).
Kontrollér `teams` for den nye liga bagefter: holdmatchen er fuzzy på normaliserede navne (inden for ligaen), så dubletter skal fanges her.
Opret et ekstra cron-job til automatisk opdatering — og skriv det i `docs/CRON.md` i samme ombæring.
Er turneringen synlig, indgår dens kampe straks i rundeligaen og i konkurrence-oprettelsen. Vil du forberede den i ro, så sæt `is_visible = false` og tænd den, når den er verificeret.
Ingen kodeændringer nødvendige, hvis leverandøren allerede er kendt. En HELT ny leverandør kræver et modul i `api/providers/` (se kontrakten i `index.js`) og et navn i check-constrainten `leagues_provider_check`. *(Var det ikke helt før 31. juli 2026: sæsonchampionshippet fandt turneringen via navne-regexet `/superliga/i`. Det er erstattet af en vælger — afsnit 5.)* Fasenavne på dansk kræver dog en linje i `STAGE_LABELS` (`src/lib/scoring.js`); uden den vises Sportmonks' rå engelske navn.

## 12. Kendte begrænsninger
Dette afsnit beskriver **vilkår** — det, der er sådan, og som ingen har tænkt sig at lave om. Det, der skal gøres noget ved, står som `G#`-rækker i [`docs/BACKLOG.md`](docs/BACKLOG.md), så en opgave ikke bor to steder. *(Skellet er indført 31. juli 2026, fordi afsnittet ikke havde det: det beskrev en fil-opdeling som "næste naturlige oprydning" tre uger efter den var leveret, og henviste til Liga Health Score og beslutning A12, som begge var fjernet. En begrænsning ældes ikke — en to-do gør.)*
Superliga-slutspillet (mesterskabs-/nedrykningsspil) er ikke en separat liga, men *stages* i hovedsæsonen hos Sportmonks. De synkroniseres derfor automatisk sammen med grundspillet — men først når Sportmonks har skemalagt kampene (formentlig til foråret). **Siden `A20` (31. juli 2026) er det ikke længere et problem:** en `full_season`-konkurrence oprettet i august efterfyldes med slutspilskampene, når de udgives (afsnit 3). Den gamle formulering — *"en konkurrence scoped til fx mesterskabsspil kan først oprettes, når kampene er udgivet (bevidst valg — ingen live-auto-tilknytning)"* — gælder ikke mere; fase-scope findes ikke, og efterfyldningen er netop den auto-tilknytning, der dengang blev fravalgt. (Den tidligere skjulte "Superliga Playoff"-liga byggede på en fejlantagelse og er fjernet — se `sql/matches_stage.sql`.)
Fasenavne er ikke fælles på tværs af turneringer — og heller ikke på tværs af sæsoner i samme turnering. Superligaen deler sig i `Championship Round`/`Relegation Round`; Scotland Premiership kalder det `1st Phase`/`2nd Phase` i 2026/2027, men brugte `Regular Season` + `2nd Phase` i 2025/2026 (aflæst 31. juli 2026). `STAGE_LABELS` i `src/lib/scoring.js` kortlægger derfor flere engelske navne til samme danske ord, og en ny turnering kræver en linje dér, før faserne står på dansk — indtil da vises Sportmonks' rå navn, hvilket er kosmetik og ikke en fejl. Skotland får desuden kun ÉN stage for hele slutspillet, så top-6 og bund-6 kan ikke skelnes, som de kan i Superligaen; derfor hedder den "Slutspil" og ikke "Mesterskabsspil".
Championship måler på to niveauer, og det samlede belønner bevidst bredde. Den samlede runde-/månedsstilling summerer point på tværs af alle officielle turneringer, så den, der tipper flere turneringer, kan score mere — det er en **udtalt regel**, ikke en skævhed, der skal rettes: titlen "Prediction Champ" er for hele fodbold-ugen. Vil man sammenligne æbler med æbler, er det per-turnering-stillingen (alle målt på de samme kampe) eller ratingen (point pr. kamp). En samlet **sæson**stilling på tværs af turneringer findes bevidst ikke. *(Vilkåret er nyt 31. juli 2026 og afløser A2; begrundelsen står i `docs/DECISIONS.md`.)*
Alle kan oprette konti uden godkendelse — fint til en lukket venneflok.
Push-notifikationer kræver opt-in pr. enhed (afsnit 16); der er ingen e-mail-påmindelser. På iOS virker push kun, når appen er føjet til hjemmeskærmen (iOS 16.4+).
Koden er opdelt i moduler (afsnit 1). **Den store fil-opdeling er halvt gennemført (30. juli 2026):** `data.js` (761 linjer) er delt i otte tematiske moduler under `src/lib/data/` bag en barrel, `PredictionsScreen.jsx` er gået fra 705 til 399 linjer og `AnalyticsPanel.jsx` fra 646 til 42. Tilbage står `MainApp.jsx` ~480, `HjemTab.jsx` ~450, `CreateCompetitionScreen.jsx` ~420 og `AdminScreen.jsx` ~310 — følges som `G1` i [`docs/BACKLOG.md`](docs/BACKLOG.md). Analytics v1 lagde bevidst sin egen logik i en ny fil (`src/lib/analytics.js`) fremfor at gøre `data.js` større end nødvendigt, men de få linjer events, der hænger sammen med eksisterende skrivninger (liga/konkurrence), blev tilføjet direkte i `data.js`, hvor de skrivninger allerede bor. *(Rettet 31. juli 2026: afsnittet beskrev indtil da `PredictionsScreen.jsx` ~700 og `data.js` ~760 som næste opgave — tilstanden før opdelingen, som var leveret tre uger forinden og står i både ROADMAP og changelog. Det er selve grunden til, at opgaverne er flyttet ud i backloggen: en to-do, der bor i den tekniske dokumentation, opdateres ikke sammen med koden.)*
Rating-genberegningen er stadig en fuld genberegning fra bunden og kører kun, når et resultat reelt ændres (afsnit 5) — men **selve beregningen er nu ~175× hurtigere** (30. juli 2026). En hel sæson med 31 spillere gik fra **19,8 sekunder til 0,1 sekund**. *(Rettet efter måling: dette afsnit anbefalede tidligere "sortér + histogram i stedet for alle-mod-alle". Det sigtede mod den forkerte flaskehals — alle-mod-alle-selvjoinet producerede 930 rækker på 0,6 ms. Hele omkostningen lå i ét udtryk: `power(10, numeric)` i den logistiske forventningsværdi. numeric-potens med ikke-heltallig eksponent regner i vilkårlig præcision og koster ~110 µs pr. kald, og med 930 spillerpar pr. runde stod den ene linje for 16 af de 19 sekunder. Rettelsen var at regne logistikken i `double precision`; alt andet er uændret.)* Målt (PostgreSQL 16.13, 10 kampe pr. runde, 85% tip-dækning): 10 runder × 31 spillere 534 ms → 42 ms; 20 × 31 3.044 ms → 54 ms; 38 × 31 19.821 ms → 101 ms; 38 × 60 76.654 ms → 252 ms; 38 × 150 **469.674 ms → 993 ms**. Bemærk den sidste: ved 150 spillere tog en genberegning knap otte minutter, og den kører **synkront i triggeren på `matches`** — altså inde i den sætning, `api/sync-live.js` bruger til at færdigmelde en kamp. Det var en tikkende bombe, ikke et teoretisk problem. To ting, der blev målt og IKKE hjalp, og derfor bevidst ikke er med: indeks på `predictions(match_id)` (1.240 → 1.124 ms, inden for støjen) og indeks på temp-tabellen `_rs(round_key)` (gjorde det langsommere, 985 → 1.184 ms). En egentlig **inkrementel** beregning er dermed ikke længere nødvendig ved realistiske størrelser; skal den laves en dag, kræver den `rounds_played` i `rating_history` for at kunne genskabe K-faktoren ved en vilkårlig rundegrænse (se `sql/rating_core.sql`). Ækvivalensen er låst fast af `sql/tests/rating_equivalence.sql`, som kører i CI mod en frisk PostgreSQL og sammenligner med den frosne før-optimering-udgave: rangorden, `rnk` og `provisional` skal være identiske, og tallene må afvige med højst 1e-9 (målt: 2e-13).
Skemaet er nu versioneret i git: hele `public`-skemaet (struktur — tabeller, views, funktioner og grants, uden data og uden ejer-info) ligger i `sql/schema.sql`, genereret af skema-eksport-workflowen (`.github/workflows/schema-export.yml` — manuelt + ugentligt; guide i `sql/README.md`). Tidligere lå kun de enkelte migrerings-scripts i repoet. Bemærk begrænsningerne: `schema.sql` er et *øjebliksbillede*, ikke migrerings-kilden (skemaændringer laves fortsat via nye scripts i `sql/`, som workflowen så fanger i næste dump), det dækker kun `public` (ikke Supabase-interne skemaer som `auth`/`storage`), og det indeholder ingen data.
**Øjebliksbilledet er friskt pr. 31. juli 2026.** Eksporten er kørt efter `multi_provider.sql` og dækker `leagues.provider`, `leagues.live_enabled` og `leagues.is_official`. Reglen er eksport efter hver migrering — en `schema.sql`, der er ældre end den seneste migrering, er ikke bare ufuldstændig, den er misvisende: den ligner en fuld sandhed.
Preview og produktion deler database, medmindre staging-variablerne er sat (afsnit 9) — selve staging-projektet skal oprettes manuelt i Supabase. Opgaven med at oprette det følges som `G4` i [`docs/BACKLOG.md`](docs/BACKLOG.md).
**Fem turneringer har ingen livescore — det er vilkåret for, at de er gratis.** Premier League, Champions League, Bundesliga, Serie A og Primera División kommer fra football-data.orgs gratis-plan, som leverer forsinkede resultater og intet spilleminut. Deres kampe får derfor aldrig live-kort på Hjem; de skifter fra "I gang" til det endelige resultat, når leverandøren melder slut. **Point er upåvirkede** — de kommer altid fra det endelige resultat. Vilkåret er sat som `leagues.live_enabled = false` og ikke i kode, så det ophører med at gælde i samme sekund €12/md-planen tegnes og flaget vendes.
Champions League' knockout-kampe findes først i kampprogrammet, når de er lodtrukket. Runder kan derfor have huller frem til lodtrækningen, og en konkurrence scoped til fx ottendedelsfinalerne kan først oprettes bagefter — samme vilkår som Superliga-slutspillet ovenfor, af samme grund.
Samme hold findes én gang pr. turnering. `teams` er scopet til `league_id`, så Arsenal i Premier League og Arsenal i Champions League er to rækker med hver sit `api_team_id`. Det er ikke en fejl, men det betyder, at holdstatistik aldrig går på tværs af turneringer.
Live-resultaternes opløsning afhænger af Sportmonks-planen: spilleminuttet kommer fra `include=periods` (den tikkende periode). Er `periods` ikke med i abonnementet, vises kampen stadig live med nuværende stilling — bare uden minuttal ("LIVE" i stedet for "LIVE 63′"). Er en kamp slet ikke tilgængelig i planen, falder Hjem-kortet tilbage til den gamle "I gang"-tekst. Selve pointene er upåvirkede, da de altid kommer fra det endelige resultat.
Analytics v1 (afsnit 21): hændelsesloggen (`analytics_events`) er fire-and-forget og dermed lossy by design — den må aldrig bruges til noget en bruger kan bestride. Prediction Completion Rate (North Star) læser derfor altid `predictions`/`matches` direkte, aldrig hændelsesloggen. Retention længere tilbage end `user_activity_days`s startdato er umålelig og vises som "Ingen data endnu", ikke som 0% (samme begrænsning, som allerede gælder den eksisterende DAU/WAU/MAU-statistik). ## 17. Story Engine v1.1 (`sql/story_engine.sql`)
Regelbaseret historie-motor (ingen AI). Fuld spec: `docs/features/story-engine-v1.md`. Når en runde afsluttes, får hver bruger én historie om, hvad runden betød *for dem*.

Beregning: `generate_stories(round_key)` (`security definer`, idempotent — sletter og genberegner rundens rækker) kaldes sidst i matches-triggeren (`sql/rating_trigger_optimization.sql`), efter `recompute_ratings()`, i rækkefølgen point → stillinger → ratings → historier. Kaldet er pakket i en exception-guard, så en fejl i historik-genereringen ALDRIG kan rulle resultat-lagring eller rating tilbage (best-effort). Kun runder, hvor alle kampe har resultat, genererer historier.

**`round_key` har TO typer i skemaet — bland dem aldrig.** `matches.round_key` er en genereret **`date`**-kolonne, og alt afledt af den er også `date`: `round_standings.round_key` og temp-tabellerne `_se_rp`/`_se_pair` inde i `generate_stories`. Derimod er `stories.round_key` og `rating_history.round_key` **`text`**. Postgres har ingen `date <= text`-operator, så én usammenlignet blanding fejler hele funktionen — og bag exception-guarden sker det **tavst**, hvilket er usynligt, fordi et tomt historie-kort ikke kan skelnes fra en stille uge. Derfor konverterer `generate_stories` sin text-parameter ÉN gang til `v_round date` og bruger `v_round` mod date-kolonnerne og `p_round_key` mod text-kolonnerne; triggerens `_se_changed_rounds` er tilsvarende `date` og caster eksplicit ved kaldet (`generate_stories(v_round::text)`). Se afsnit 13 og changelogen (juli 2026).

Regelkatalog (prioritet, lavest vinder) — **14 regler i to tiers** siden v1.1:

*Højdepunkter (prioritet < 90):* 10 Månedens Champ · 20 Førsteplads overtaget · 21 Førsteplads mistet · 22 Ind i top 3 · 30 Ny ratingrekord · 40 Head-to-head-overhaling · 45 Tæt på toppen · 50 Comeback · 55 Personlig runderekord · 60 Stime mod rival · 70 Rundens vinder · 80 Perfekt træfsikkerhed.

*Dæmpet tier (prioritet ≥ 90):* 90 Premiereugen (`SEASON_OPENER`) · 100 Stille runde (`QUIET_ROUND`). Disse to genereres **kun** for brugere, der efter alle øvrige regler ville stå helt uden en række i runden — de kan derfor aldrig konkurrere med en rigtig historie.

**Tre regler har to prioriteter.** Tærsklen blev sænket i v1.1 (comeback fra 2 pladser, stime fra 2 sejre, præcise fra 2), men den svage variant får et højere prioritetstal: comeback 50/**75**, stime 60/**75**, præcise 80/**85**. 75 ligger under rundens vinder (70), så en svag variant aldrig fortrænger en stærk historie. Princippet: *tærsklen afgør, om historien findes; prioriteten afgør, om den vises.* Prioriteterne er ét sted i JS (`RULES`, `SOFT_PRIORITY`, `priorityFor` i `src/lib/stories.js`) og spejles af `case`-udtryk i SQL'en.

Pr. bruger pr. runde vælges én via viewet `latest_story` (laveste prioritet → største liga `league_size` → `competition_id`). Alle udløste kandidater gemmes (råmateriale til minde-arkiv senere) — men karriereprofilens milepæle henter kun `priority < 90` (`loadCareerMilestones`), da dæmpede kort ikke er minder.

Data & RLS: `stories` (payload + færdig `headline`/`body` + `league_size`-snapshot). RLS: en bruger kan kun læse/afvise egne historier. Skrivning sker kun via `generate_stories()`.

Frontend: historie-kort på Hjem, direkte under tips-status-kortet, altid synligt (viger ikke for deadline). **To udgaver, styret af prioriteten** (`isQuiet`, `src/lib/stories.js`): et **højdepunkt** (< 90) er guld-fremhævet, har emoji i overskriften og en Del-knap; et **dæmpet** kort (≥ 90) er et almindeligt kort med mindre overskrift, uden emoji og **uden Del-knap** — der er intet at prale af. Begge kan afvises. Helpers `loadLatestStory`/`dismissStory` (`data.js`); ren regel-/tekst-logik i `src/lib/stories.js` (enhedstestet). "Del" deler headline+body (`navigator.share`, fallback udklipsholder); "Afvis" sætter `dismissed_at`.

**Deltager-afgrænsning (ufravigelig).** `_se_rp` — tabellen alle regler læser deres stilling og deres navne fra — joiner `competition_participants`. `predictions` er global pr. `(bruger, kamp)` og ved intet om konkurrencer, så uden det join tælles enhver, der har tippet den samme kamp i en anden konkurrence, med i denne konkurrences stilling. To konkurrencer på samme turnering deler alle deres kampe, så det er reglen, ikke undtagelsen. Heraf følger designreglen: **en historie må kun nævne personer, modtageren deler konkurrence med** — alle fire navngivende regler (21, 40, 45, 60) henter personen fra `_se_*`-tabellerne, og en fremtidig regel skal gøre det samme. Se changelogen (juli 2026) for fejlen, det kostede at opdage.

Tone: teksterne driller, men ydmyger aldrig. I det dæmpede tier er reglen **kodet**, ikke kun beskrevet: placeringen nævnes kun i tabellens øverste halvdel (`rank * 2 <= total`); i den nederste står afstanden op til toppen og en fremadrettet slutning. Dækket af en enhedstest.

Synlighed: kortet er live for alle brugere (skyggetilstand fjernet, juli 2026). `HjemTab` henter `loadLatestStory` for enhver bruger — tidligere var hentningen gated på `profile.is_admin`.

Engangsopsætning: kør `sql/story_engine.sql` i Supabase ("Run without RLS"), og gen-kør `sql/rating_trigger_optimization.sql` (hooker `generate_stories` ind i triggeren). Ved en ren v1.1-opdatering er kun det første nødvendigt — triggeren er uændret. Bemærk, at allerede afsluttede runder ikke får de nye regler af sig selv (`generate_stories` kaldes kun, når et resultat ændres). Til det findes `sql/story_engine_backfill.sql`, som kalder funktionen én gang pr. **fuldt** afsluttet runde — med samme komplethedsfilter som triggeren, så en delvist spillet runde aldrig får historier ud fra en halv stilling. ## 18. Liga-laget (`sql/groups.sql`)
Den permanente liga-enhed (fællesskabet), som konkurrencer lever indeni. Fuld spec: `docs/features/liga-laget-v1.md`.

Ordbog (vigtig — "liga" var før tvetydig): **turnering** = fodboldliga fra Sportmonks (`leagues`), **liga** = fællesskabet (`groups`), **konkurrence** = tippekonkurrence (`competitions`). Al brugervendt tekst følger ordbogen; DB-navne (`leagues`, `league_id`) er uændrede.

Datamodel: `groups` (navn, `invite_code`, `created_by`) + `group_members` (`(group_id, user_id)`, `role` ∈ `admin/member`) + `competitions.group_id` (nullable, `on delete set null`). Sletter man en liga, bliver dens konkurrencer liga-løse (slettes aldrig).

RLS: `groups` er læsbar for alle authenticated (nødvendigt for join-med-kode). `group_members` læses via `security definer`-funktionen `is_group_member(gid)` — policyen slår ALDRIG direkte op i `group_members` (ville give "infinite recursion", jf. afsnit 13). `is_group_admin(gid)` gater omdøb/sletning. Man melder kun sig selv ind (`user_id = auth.uid()`); kun ligaens opretter må indsætte sig som `admin`. `competition_participants` har en ny DELETE-policy: forlad en konkurrence, men ikke med tips på allerede låste kampe (genbruger runde-lås-udtrykket fra afsnit 2). **Bemærk:** policyen er siden udvidet med en gren mere — se "Framelding fra en konkurrence gælder kun midt i et forløb" nedenfor, som er den gældende regel. Sletning af en liga kræver admin + at den er tom (ingen konkurrencer).

Blød migrering: eksisterende konkurrencer har `group_id = null` og virker uændret ("Øvrige konkurrencer" på Ligaer-fanen). Ingen automatisk gruppering. Opretteren flytter selv en konkurrence ind i en liga via `move_competition_to_group(comp_id, group_id)` (`security definer`; guard: kalderen ejer konkurrencen og er medlem af ligaen) — konkurrencens deltagere bliver automatisk liga-medlemmer.

Frontend: `GroupScreen.jsx` (liga-siden), omstruktureret `LigaerTab.jsx` (ligaer øverst + samlet join-felt + engangs-nudge), liga-dropdown i `CreateCompetitionScreen.jsx`, `?liga=<kode>`-deep-link i `App.jsx`/`MainApp.jsx`, og Hjem-fanens "Dine placeringer" grupperet pr. liga (`Placements`-komponent i `HjemTab.jsx`). Data-helpers i `data.js` (`loadMyGroups`, `loadGroupDetail`, `createGroup`, `joinGroup`, `leaveGroup`, `deleteGroup`, `joinCompetition`, `leaveCompetition`, `moveCompetitionToGroup`, `loadGroupByCode`). Enhedstests i `data.test.js`.

**Invitationer — to links, begge permanente (A7, juli 2026).** `?liga=<kode>` inviterer til fællesskabet; `?join=<kode>` inviterer direkte til én konkurrence. **Stedet afgør:** Invitér-knappen på liga-siden (`GroupScreen`) deler altid liga-linket, knappen på en konkurrences side (`BoardScreen`) altid konkurrence-linket. `BoardScreen` erstattede tidligere stiltiende konkurrence-linket med liga-linket for liga-konkurrencer, så man ikke kunne invitere til én bestemt konkurrence — substitutionen er fjernet, og med den `groups`-opslaget i skærmen. **A8 håndhæves i DATABASEN** (`sql/group_membership_invariant.sql`, juli 2026). Invarianten er: *ingen kan være deltager i en liga-konkurrence uden at være medlem af ligaen.* Den forældreløse tilstand er synligt forkert — deltageren står i konkurrencens stilling, men mangler på ligaens medlemsliste og kan ikke åbne ligaens side. Tre huller, tre svar:

1. **Eksisterende rækker** — engangs-backfill indsætter de manglende `group_members` (rolle `member`; `on conflict do nothing`, så en admin-række aldrig nedgraderes).
2. **Nye deltagere** — trigger `competition_participants_ensure_group` (`before insert`, `security definer`) indmelder automatisk i ligaen. Auto-indmelding frem for afvisning, fordi A8 siger, at deltagelse i en liga-konkurrence *er* liga-medlemskab: det er én handling, ikke en betingelse. Så kan ingen kaldesti glemme rækkefølgen — præcis den fejl, A7 afdækkede. Klienten (`joinCompetition` i `data.js`) gør det stadig eksplicit, så bekræftelses-modalen kan sige det til brugeren; triggeren er sikkerhedsnettet, ikke forklaringen.
3. **At forlade ligaen** — dette var det vigtigste hul: `leaveGroup` slettede kun `group_members`-rækken og skabte dermed forældreløse deltagere *efter* at alt var gået rigtigt til. DELETE-policyen `group_members_delete_self` blokerer nu, så længe man deltager i en af ligaens konkurrencer. `leaveGroup` returnerer `false` ved blokering, og `GroupScreen` forklarer: "Frameld dig dem først."

**Framelding fra en konkurrence gælder kun midt i et forløb.** Den oprindelige `comp_participants_delete_own_unlocked` blokerede, hvis man havde tips på låste kampe — men en spillet kamp bliver aldrig uspillet, så spærren var i praksis permanent. Sammen med punkt 3 ville det gøre det umuligt nogensinde at forlade en liga, man havde spillet én runde i, og da admin-fjernelse af andre medlemmer bevidst ikke er bygget, ville der ikke være nogen vej ud. Policyen tillader nu framelding, når **alle konkurrencens kampe har resultat** (forløbet er forbi og kan ikke skjules); er der kampe tilbage, gælder historik-beskyttelsen uændret. Nettoreglen: mens en konkurrence kører, er man bundet til ligaen; når dens kampe er spillet, kan man melde sig ud af begge.

Engangsopsætning: kør `sql/group_membership_invariant.sql` ("Run without RLS"). Verifikationsforespørgslen står nederst i scriptet og skal give 0 rækker.

Engangsopsætning: kør `sql/groups.sql` i Supabase ("Run without RLS"). Verificér i staging først, og tjek kolonne-/tabelnavne mod `sql/schema.sql` (fuldt skema-øjebliksbillede, afsnit 12). Tjek eksplicit for "infinite recursion" på `group_members` (kendt fælde).

Ét RPC `career_profile(profile_user_id uuid)` (`security definer`, `set search_path = public`, mønster som `admin_user_stats()`) returnerer al profil-data som `jsonb`: hoved (`profiles`, `ratings`, seneste `rating_history.delta`), titler (sæsontitler fra `season_standings` + månedstitler fra `monthly_standings` + rundesejre fra `round_standings`, kun for **afsluttede** sæsoner/måneder/runder = alle kampe spillet), ratingkurve (`rating_history`), basistal, `h2h`, `records`, `footprint` og rivaler.

`titles.by_tournament` (K2, 31. juli 2026) er svaret på, hvad en titel betyder, når Championship kårer på to niveauer (afsnit 5). Grenen indeholder ét objekt pr. **officiel** turnering med turneringens månedstitler og rundesejre — læst fra `scope = <league_id>` — og `ProfileScreen` viser den som en **adskilt** sektion under de samlede titler, med dæmpede badges og sin egen `InfoDot`. De eksisterende grene (`monthly`/`season`/`round_wins`) er og forbliver **kun** de samlede: ellers ville "Månedens Prediction Champ ×5" betyde noget andet efter turnering #3 end før, og et karrieretal, hvis betydning skifter, når produktet vokser, kan ikke sammenlignes med sig selv. En turnering vises kun, hvis brugeren har vundet noget i den, så en ny turnering ikke giver enhver profil en tom overskrift. Komplethedsjoinene er **pr. turnering**: en manglende skotsk kamp må ikke holde Superligaens månedstitel tilbage. Per-turnering-*rating* (`ratings.scope`) er stadig ikke besluttet og er bevidst ikke en del af dette.

`titles.season` (juli 2026) lukker et hul: Championship har **tre** kåringer (runde, måned, sæson), men karrieren registrerede kun de to første, så den største af dem aldrig ville stå nogen steder, når sæsonen sluttede. Samme regler som månedstitlen — kun afsluttede sæsoner (`bool_and(home_score is not null …)` pr. `season_id`), `rank()` frem for `distinct on` (en delt titel er en titel for begge) og hele tiebreaker-stigen inkl. `round_wins`, som `season_standings` allerede har. Badget står **først** blandt titlerne. `matches.season_id` er nullable; join'et til `seasons` filtrerer de rækker ud.

Adgang (K1, **udvidet juli 2026**): RPC'et kræver kun, at man er logget ind. Enhver indlogget bruger kan åbne enhver karriere og se hoved, titler, kurve, basistal, rekorder og fodaftryk; findes profilen ikke, kastes `not found` (skærmen viser "Profilen findes ikke længere."). Den oprindelige gate var "egen profil, eller delt liga/konkurrence" — den afviste folk, man reelt konkurrerer med (på Championship er alle automatisk med) og beskyttede intet, der ikke allerede stod offentligt på Rating-/Championship-fanerne. Milepæle og rivaler er uændret private (kun egen profil).

Privathed: milepæle og rivaler er personlige og vises kun på egen profil. Milepæle læses **separat** client-side via den eksisterende RLS på `stories` (kun egne rækker — `loadCareerMilestones` springer kaldet over for andres profil); rivaler kommer kun med i RPC-svaret, når `profile_user_id = auth.uid()`.

**Rivaler — K3 lukket (30. juli 2026): rangeres på jævnbyrdighed fra faktiske møder, ikke på antal historier.** Hver rival er `{ user_id, rival, meetings, wins, losses, draws, stories }`, sorteret efter `abs(wins - losses)` asc, `meetings` desc, `rival_id` asc (sidste nøgle sikrer et deterministisk svar), maks. 3, og kun modstandere med `meetings >= v_rival_min_meetings` (navngivet, tunbar variabel i funktionen, pt. **2** — samme princip som Story Engines kalibrerede tærskler: ét møde gør ingen til en rival, men en høj tærskel i en ung sæson giver nul rivaler).

Møde-tallene bruger **præcis samme semantik som `h2h`**: et møde er én `round_key`, hvor begge har tippet en kamp fra en konkurrence, de deler, dedupliceret pr. kamp på tværs af delte konkurrencer, og hver side tæller de kampe, den selv har tippet (som `round_standings`, der heller ikke normaliserer for antal tippede kampe). Det er ikke en detalje: `rivals`-posten om en person og `h2h`-linjen på den persons profil skal svare det samme på samme spørgsmål — verificeret som invariant.

Den tidligere metode var ren story-optælling af `payload->>'rival'` for regel `H2H_PASS`/`STREAK`. K3 valgte den som billigste udgangspunkt og forudsagde selv problemet ("udvid hvis den giver for få rivaler i små ligaer"): kun 2 af 14 regler skriver et rival-navn, regel 40 kræver en overhaling i netop den runde, regel 60 en **aktuel** stime på ≥2 sejre, og begge har `distinct on (competition_id, user_id)` — altså én rival pr. konkurrence pr. runde. I en lille liga med stabil rækkefølge giver det nul rivaler efter mange runder mod de samme personer. Historierne er beholdt som `stories`-feltet, altså **farve**, aldrig rangering; det joines på `display_name` (alt payloaden gemmer), så et navneskift mister tilknytningen — acceptabelt for et pyntetal, og præcis derfor rangeringen ikke hviler på det.

K3's egen foreslåede udvej, placerings-nabo-analyse på `rating_history.rnk`, er **bevidst ikke valgt**: `rnk` er den globale ratingplacering og kunne udpege folk, man ikke deler konkurrence med — i strid med designreglen fra juli 2026 (en historie må kun nævne personer, modtageren deler konkurrence med). Beregningen starter derfor i `competition_participants` og kan per konstruktion ikke nævne en fremmed. **Ingen regression:** en story-rival er altid også en møde-rival, da regel 40 kræver en stilling før runden for begge parter og regel 60 ≥2 sejre i træk — begge medfører ≥2 møder.

Fordi rivalen nu kommer med `user_id`, er navnet en **tryk-flade** som alle andre navne i appen (`PlayerName`) — spec'ens "et brugernavn er altid vejen til karrieren" gjaldt hidtil ikke her, netop fordi story-optællingen kun havde et `display_name`. `ProfileScreen` tager derfor imod `openProfile` fra `MainApp`.

**K4 (30. juli 2026) — tre nye, offentlige nøgler** (samme synlighedsniveau som hoved/titler/kurve/basistal, ikke `isOwn`-gated medmindre andet er nævnt):
- `h2h`: ét narrativt punkt, **kun ved fremmed profil** (`not v_own`) **og** kun hvis viewer og profilens ejer deler mindst én konkurrence (`competition_participants`) med mindst én fælles tippet, afgjort runde. "Et møde" = én `round_key`, hvor begge har tippet en kamp fra en delt konkurrence; point sammenlignes via `pc_points()` (samme kilde som Story Engine/stillingerne, F2). **Deduplikeret pr. kamp på tværs af delte konkurrencer** (rettelse 30. juli 2026): `predictions` er ét tip pr. bruger pr. kamp, ikke pr. konkurrence, så deler to brugere flere konkurrencer, der dækker samme kamp/runde (fx en rundebaseret + en full-season-konkurrence for samme turnering), tæller rundens møde kun én gang — ellers ville "I har mødt hinanden 2 gange" kunne vises efter kun én spillet runde. `{ meetings, wins, losses, draws }` set fra viewerens perspektiv, eller `null` hvis intet fælles møde findes (eller ved egen profil). Vises i UI uanset om viewer fører eller taber — kun tælletal, ingen superlativer. **Sætningen navngiver sit eget omfang** (30. juli 2026): den indledes "I jeres fælles konkurrencer har I mødt hinanden N gange", og en dæmpet linje under den siger "kun kampe fra konkurrencer I begge er med i — hver runde tæller én gang". Uden den indledning blev tallet læst som en global opgørelse over alt, de hver især havde tippet. Teksten bygges af den rene funktion `h2hSentence` (enhedstestet). Bevidst, afgrænset undtagelse fra beslutningen "H2H bor i Story Engine, ikke en sammenligningsside" (se ROADMAP-beslutningsloggen 30. juli 2026 og `docs/features/karriereprofil-v1.md` §8 K4): ingen tabel, ingen historik-liste, kun én sætning.
- `records`: "bedste nogensinde" — `best_rating`/`best_rating_round` (højeste `rating_after` nogensinde, `scope='ALL'`), `best_round_points`/`best_round_exact`/`best_round_points_round` (flest point i én afsluttet runde), `best_round_rank`/`best_round_rank_count`/`best_round_rank_field` (bedste rang i `round_standings`, samme `rank()`-stige som `titles.round_wins`), `longest_round_streak` (længste sammenhængende stime af rundesejre). Alle felter er `null`/`0` for en bruger uden afsluttede runder. Frontend viser kun `best_round_rank` når den er > 1 (ellers redundant med "🥇 N rundesejre"-badget), og kun `best_round_points` når den er **> 0** — "din bedste runde nogensinde: 0 point" ville drille præcis den bruger, der har mindst brug for det (fanget på rigtige data: en spiller med én runde og nul point). Linjerne står fra det mest konkrete til det mest abstrakte: bedste runde → placering → stime → ratingtal.

  **Omfanget er GLOBALT — og det er en præcis påstand** (rettelse 30. juli 2026, anden runde): rating er `scope='ALL'` (samme tal som Rating-fanen), og rundeplacering/stime måles i `round_standings`, dvs. **Championships rundeliga, hvor alle brugere er med**. Det er *ikke* en opgørelse pr. brugerens egne konkurrencer. Første rettelse satte kun en `InfoDot` på overskriften med teksten "på tværs af alle dine konkurrencer og ligaer" — den var både **skjult bag et klik** og **upræcis**: formuleringen læses som en opgørelse *pr. egen konkurrence*, mens rangen faktisk måles mod samtlige brugere med point i runden. Nu navngiver hver linje sin egen kilde ("Din bedste placering i **Championships rundeliga**", "Din højeste **globale** rating"), og InfoDot'en forklarer kontrasten mellem de to omfang.

  **Hvordan omfanget formidles (endelig form, 30. juli 2026 — tredje runde):** ét klik væk, aldrig som brødtekst på siden. Et mellemtrin gav hver sektion en **synlig** scope-linje (`scopeNote`) oven i InfoDot'en, ud fra ræsonnementet at en hjælpetekst bag et klik ikke fanger en forkert førstelæsning. **Brugeren afviste det:** fem forklarende afsnit gjorde siden tungere at skimme, end den tvivl de fjernede, var værd — *"det skal ikke stå på forsiden"*. Den holdbare regel blev derfor: **tallene navngiver deres eget omfang i selve sætningen**, og forklaringen ligger i en `InfoDot`. Hver sektion med tal har nu sin egen — Titler, Rekorder, Milepæle, Rivaler, H2H og basistallene (samt Karriere-hovedet, som altid har haft en). Kortene uden overskrift (H2H, basistal) bærer ikonet inline, efter indholdet frem for foran det. **Ny sektion med tal ⇒ ny InfoDot, ikke ny brødtekst.**

  `best_round_rank_field` er feltstørrelsen for runden (`count(*) over (partition by round_key)`), så "4. plads" kan vises som "4. plads af 31 spillere" — er samme rang sat i flere runder, bruges `max(field)`. Frontend **udelader** feltstørrelsen, når `rank >= field`: "8. plads af 8" er en bundplacering, og profilen viser aldrig bundplaceringer (`karriereprofil-v1.md` §1, punkt 3). Samme, tomme udfald gælder, indtil migreringen er kørt i produktion — feltet mangler da bare i svaret. Reglerne bor i den rene funktion `recordFacts` (`ProfileScreen.jsx`, enhedstestet i `ProfileScreen.test.jsx`), ikke i JSX.
- `footprint`: `{ leagues, competitions }` — antal rækker for brugeren i `group_members` hhv. `competition_participants`. Arkiverede (`hidden=true`) liga-løse konkurrencer tælles med (`hidden` er et personligt ryddeflag, ikke "forladt konkurrencen").

Milepælslisten (`ProfileScreen.jsx`) viser som standard kun de nyeste 20 (`MILESTONE_PAGE`), med "Vis alle N milepæle" som udvider — rent frontend-loft, ingen ændring i hvad `loadCareerMilestones` henter eller hvilke `stories`-regler der tæller som milepæl (`priority < 90`, uændret).

Samme pointkilde som stillingerne (F2): basistal og titler bruger det **identiske** 3/1-CASE-udtryk som `round_standings`/`season_standings`, så profilens tal altid matcher Championship-fanen for samme bruger. Basistallene beregnes karriere-bredt (alle spillede kampe) — med kun én sæson identisk med `season_standings`.

Frontend: `loadCareerProfile`/`loadCareerMilestones` (`data.js`, enhedstestet i `data.test.js`). Ratingkurven tegnes som en letvægts inline-SVG (`Sparkline` i `ProfileScreen.jsx`, ingen chart-bibliotek); de første <5 runder (provisorisk K-faktor) tegnes dæmpet/stiplet. **Toppunktet ringes ind** (◎) ud fra `records.best_rating_round`, så Rekordernes "højeste rating nogensinde" kan genfindes i kurven i stedet for at være et løsrevet tal; mangler nøglen, falder ringen tilbage på kurvens eget maksimum. **Akserne** står som HTML uden om SVG'en, ikke som `<text>` inde i den — `preserveAspectRatio="none"` ville forvrænge tekst vandret på brede skærme: y-aksen som et neutralt interval ("Skala 1200–1240", bevidst ikke "din laveste rating"), x-aksen som første og sidste rundeetiket (ikke alle — de kan ikke læses på en telefon, og kurven skal give et forløb, ikke aflæsninger). Basistallene viser også `outcome_count` ("N korrekte udfald"), som tidligere blev hentet uden at blive vist — uden det kunne pointsummen ikke stemme med antallet af præcise, medmindre brugeren selv regnede resten ud. Nås via rating-snapshot-kortet på Hjem (`openProfile(userId)`) og navne-klik i Rating-ranglisten (`RatingTab`); `MainApp` router `screen.type === "profile"`. Tom tilstand for nye brugere: hoved + venlig "din karriere er lige begyndt"-tekst, ingen nul-tabeller.

Engangsopsætning: kør `sql/career_profile.sql` i Supabase ("Run without RLS"). Idempotent. **Gen-kør filen efter leverancerne 30. juli 2026** — de tilføjer `records.best_round_rank_field`, `records.best_round_points`/`best_round_exact`/`best_round_points_round` og `titles.season`. Frontenden er bagudkompatibel med den gamle funktion (feltstørrelse, bedste runde og sæsontitel udelades bare), så rækkefølgen er fri.

**Verificeret mod en rigtig PostgreSQL 16.13** (ikke kun mod `sql/schema.sql`, som er et bagudliggende øjebliksbillede, afsnit 12): produktionsskemaet + `standings_tiebreakers.sql` + `career_profile.sql` indlæst i en tom database, 4 spillere over 3 afsluttede runder med håndregnet facit, plus en færdigspillet sæson. Bekræftet: `round_standings` matcher facit række for række; `titles.season` udløses kun for den faktiske vinder og **forsvinder**, når ét resultat fjernes (sæsonen er ikke længere afsluttet); `titles.round_wins` følger samme regel; `best_round_points` vælger ved pointlighed den ældste runde; `best_round_rank_field` er rundens feltstørrelse; en helt ny bruger giver `null`/`0` på alle `records`-felter og tomme titel-arrays; og filen er idempotent (to gen-kørsler, nul fejl, funktionen svarer stadig). Kørslen fandt én reel fejl inden levering: en spiller, hvis eneste runde gav nul point, ville have fået "din bedste runde nogensinde: 0 point" — deraf `> 0`-guarden.

## 21. Analytics v1 (`sql/analytics_events.sql`, `sql/analytics_dashboard.sql`)

Internt måle-lag — til produktforbedring, ikke marketing. Fuld spec: `docs/features/analytics-v1.md`.

North Star: **Prediction Completion Rate** (afgivne tips / mulige tips, pr. bruger/liga/konkurrence/uge/måned), beregnet af ét view, `analytics_completion_facts`: én række pr. muligt tip (kampe i konkurrencer brugeren deltager i, i runder der allerede er låst, og som låste efter brugeren meldte sig til). "Afgivet" = rækken findes i `predictions` — pålideligt uden tidsstempel, fordi `sql/predictions_write_lock.sql` allerede forhindrer skrivning efter deadline. Grain-reglen (vigtig, letter at få galt): `count(distinct (user_id, match_id))` pr. bruger/liga/uge/måned (`predictions` er delt på tværs af konkurrencer og må ikke tælles dobbelt); almindeligt `count(*)` pr. konkurrence.

Hændelseskatalog: se `docs/features/analytics-v1.md` afsnit 3 for den fulde liste. **Tre events fra den oprindelige specifikation logges bevidst IKKE**: `prediction_locked` (udledt af `analytics_match_locks`, en omskrivning af låsen fra `predictions_match_lock.sql` — rører aldrig selve lock-policyerne), `story_generated` (findes allerede som en række i `stories`) og `push_sent` (findes allerede som en række i `notification_log`).

Skrivning: `analytics_events` (`event_id`, `event_name`, `user_id` default `auth.uid()`, `group_id`/`competition_id` nullable `on delete set null`, `metadata` jsonb, `created_at`). RLS: kun INSERT af egne rækker (`user_id = auth.uid()`) — ingen SELECT/UPDATE/DELETE for almindelige brugere. Klienten skriver **fire-and-forget** via `logEvent(token, name, {groupId, competitionId, metadata})` i `src/lib/analytics.js` — samme kontrakt som den eksisterende `touchActivity()`: intet awaites, alle fejl svælges. `logEventOnce` bruges til impressions (`story_viewed`), så et faneskift ikke tæller samme visning flere gange. `opened_*`-navigation throttles 20 sekunder for at undgå dobbelttælling ved hurtigt fane-skift/StrictMode; writes (`prediction_saved` m.fl.) throttles ALDRIG.

Læsning: seks `security definer`-RPC'er, hver bag `analytics_require_admin()` (samme `is_admin`-mønster som `admin_user_stats()`): `admin_analytics_health(p_days)` (Produktets sundhed — aktive brugere, ligaer, konkurrencer, North Star, Deadline Miss Rate, gennemførte runder), `admin_analytics_engagement(p_days)` (view-tal, Push Open Rate, gennemsnitlig sessionstid via 30-min. inaktivitetsgrænse), `admin_analytics_league_health(p_days)` (Health Score, se nedenfor) `admin_analytics_retention()` (uge 1/4/12/26/52), `admin_analytics_funnel(p_days)` (tragt for nye brugere) og `admin_analytics_stories(p_days)` (Story Engine pr. regel). Alle grants er `to authenticated` — RPC'erne selvgater internt, ingen adgang til `anon`.

**Tragt for nye brugere** (`admin_analytics_funnel`, 30. juli 2026, ROADMAP A13): fire trin — konto → liga → konkurrence → første tip — splittet på **selvstarter** og **inviteret**. Alt udledes af `profiles`/`group_members`/`competition_participants`/`predictions`, ALDRIG af hændelsesloggen: `account_created` m.fl. findes i kataloget, men loggen er fire-and-forget, og en tragt, der undervurderer sit eget første trin, er værre end ingen tragt. Vejen ind afgøres af den FØRSTE liga, brugeren kom med i (egen = selvstarter); en bruger helt uden liga regnes som selvstarter, fordi A8-invarianten indmelder i ligaen i samme øjeblik en invitation accepteres. Svaret er én flad `rows`-liste fra `grouping sets` (to scopes × total + hver vej), som klienten plukker i (`funnelRow`). **To forskellige frafalds-tal, og forskellen er vigtig:** trin-tællingen viser, hvem der nåede hvert trin overhovedet, mens "hvor står de nu" er en ÆGTE partition (hver bruger tælles præcis ét sted). De to er ikke det samme, fordi trinnene ikke er strengt indlejrede — en liga-løs konkurrence kan nås uden en liga. Tid til første tip er en ØVRE grænse: `predictions` har ingen `created_at`, kun `updated_at`, som flytter sig når et tip rettes.

**Story Engine pr. regel** (`admin_analytics_stories`, 30. juli 2026): genereret/afvist fra `public.stories` (rigtige rækker, præcise) holdt ADSKILT fra vist/delt fra `analytics_events` (`metadata->>'rule'`, fire-and-forget, et gulv) — forskellen i pålidelighed afgør, hvad man må konkludere. `dismissed_at` er brugerens eneste AKTIVE afvisning og findes pr. række uden gulv-forbehold. Plus permanent **dækningsmåling** (brugere med en historie ÷ brugere med en låst runde), det tal v1.1 blev målt på. Regelkatalogen med de 14 regler bor i `STORY_RULES` (`src/lib/analytics.js`), fordi RPC'en per definition kun kan se regler, der HAR udløst — og det interessante er, hvilke der aldrig har. **ALDRIG** (har aldrig udløst) skelnes fra **STILLE** (udløst før, men ikke i vinduet). En test læser `sql/story_engine.sql`, trækker regelnavnene ud og fejler ved drift.

**Push-effekt** (inde i `admin_analytics_engagement`'s `push`-objekt, 30. juli 2026): open rate siger, om beskeden blev åbnet — dette siger, om den virkede. Enheden er (bruger, runde); modtagerne findes ved at parse `notification_log.key` (`deadline:<season_id>:<round_key>:<dato>`, felt 3 er runde-nøglen, med et defensivt regex-tjek så en uventet nøgle udelades frem for at tage hele sektionen med sig), og "tippede" læses fra `analytics_completion_facts`. ⚠️ **Korrelation, ikke årsag** — de, der åbner notifikationer, er de engagerede i forvejen, så forskellen er et LOFT over effekten. Varsel før rundelås (`sent_at` → `lock_at`, i intervaller) er med, fordi cron-tidspunktet er den eneste knap, der reelt kan drejes på.

**Liga-diagnose** (afløste Liga Health Score 30. juli 2026, ROADMAP A12). Den gamle score var ét sammenvejet 0-100-tal med fem vægte. Den blev fjernet, fordi den var for bred: de fire første rigtige ligaer fik 75/77/77/88 — alle grønne, alle "SUND" — så den kunne hverken skelne ligaer fra hinanden eller sige HVAD der var galt, og tre af de fem faktorer målte reelt det samme ("kommer medlemmerne her").

`admin_analytics_league_health(p_days)` returnerer nu **målte signaler pr. liga uden score og uden tilstand**: bredde (medlemmer med ≥1 afgivet tip ÷ medlemmer), deltagelse (North Star for ligaens konkurrencer), retning (mod forrige lige så lange vindue), puls (spillede runder ÷ låste runder), koncentration (den mest aktive tippers andel af ligaens tips), aktive medlemmer, fastholdelse, konkurrencer (i alt / i gang), seneste aktivitet og story views. Alle deltagelses-signaler kommer fra `analytics_completion_facts` — samme kilde som North Star, så liga-tallene og "Produktets sundhed" ikke kan modsige hinanden. **Bredde er det signal, v1 manglede helt:** den gamle "andel aktive medlemmer" målte, om folk ÅBNEDE appen, ikke om de SPILLEDE.

**Tilstanden udledes i klienten**, ikke i SQL: `diagnoseLeague()` i `src/lib/analytics.js` evaluerer 12 regler oppefra og ned, og den første, der passer, vinder (for ny → død → ingen konkurrence → i dvale → kun ét medlem → intet at måle på → ingen tipper → bæres af én → kun en del tipper → deltagelsen falder → lav deltagelse → sund). Rækkefølgen er selve designet: **årsag før symptom** — en liga uden aktiv konkurrence hører "opret en konkurrence", ikke "for få tipper". "For ny" står først, så en liga oprettet i går aldrig stemples "Død". Hver tilstand giver en begrundelse med ligaens egne tal og en handling. Tærsklerne står samlet i `LEAGUE_THRESHOLDS` og kan overstyres pr. kald — de kræver ingen SQL-kørsel og er unit-testede på begge sider af hver grænse. Samme valg som Onboarding v1 (tilstand udledt af data, ingen SQL); baggrunden er, at ingen CI kører SQL, så en tærskel i en `create or replace`-funktion kun kan efterprøves i hånden.

Deadline Miss Rate ≠ Prediction Completion Rate: en bruger "misser deadline" i en runde kun ved NUL tips i den låste runde — 3 ud af 5 tippede kampe måler Completion Rate, ikke en miss.

**Vinduesregel:** dag-granulære felter (dem der læser `user_activity_days`) bruger `today - (p_days - 1)`, så `p_days = 30` betyder 30 kalenderdage inkl. i dag. Rettet 30. juli 2026 — før talte `groups_with_active_member` og Deadline Miss Rates nævner 31 dage, mens tidsstempel-baserede felter i samme svar talte 30. `rounds_completed` er bevidst **alt tid** og siger det nu i etiketten. North Star returneres desuden med `completion_rate_prev` (forrige lige så lange vindue), så tallet kan vises med en retning; nøglen er `null` — og pilen skjult — under 5 mulige tips, så støj ikke præsenteres som et fald.

**Måle-ordbogen** (`src/lib/analyticsMetrics.js`, 30. juli 2026): 36 metrikker, hver med *hvad måles / hvordan / kilde / forbehold*, vist bag en ⓘ ved hvert nøgletal. `metricInfo(id)` giver `null` for et ukendt id, så en tastefejl koster ⓘ'en og ikke sektionen. Grænsen mod skærmen er uændret (samme regel som karriereprofilen): etiketten bærer omfanget, ⓘ'en uddyber. Vigtigste felt er **forbeholdet** — hændelses- og push-tallene er GULVE, ikke facitter, fordi logningen er fire-and-forget og `notification_log` claimes før afsendelsen.

Frontend: instrumentering centraliseret i `MainApp.jsx`s `goTab`/`open*` (al navigation ét sted), `PredictionsScreen.save()` (tip-livscyklus: `prediction_started`/`saved`/`updated`/`submitted`), og `data.js`s liga/konkurrence-skrivninger. Ny admin-fane "Analytics" (`AdminScreen.jsx`, fjerde chip ved siden af Kampe/Resultater/Statistik) renderer `src/screens/AnalyticsPanel.jsx`: seks uafhængige sektioner (Tragt · Produktets sundhed · Engagement · Story Engine-regler · Liga-diagnose · Retention — brugerens rejsefølge), hver sin `useEffect`/fejlhåndtering, så én langsom eller fejlende sektion ikke blokerer de øvrige. Ingen ny chart-dependency — `StatTile`/`StatGroup`/`MiniBars` er flyttet fra `AdminScreen.jsx` til `ui/components.jsx` (nu delt med "Statistik"-fanen) sammen med `PctGrid` (retention-kohortematrix, gråtonede celler i stedet for falske 0 %'er) og, siden 30. juli 2026, `StateChip` (liga-diagnosens tilstand: ORDET er signalet, farven kun ekstra — en tilstand uden tone får bevidst ingen farve, så "vi ved det ikke" ikke ligner "det er fint") og `SignalRow`. `HealthBar` er fjernet sammen med scoren. `MiniBars` skelner nu `value: null` (ingen måling, fx en uge uden låste runder) fra et ægte 0 — samme regel som `PctGrid` allerede fulgte.

Ydelseskontrakt (ufravigelig): events logges asynkront og påvirker aldrig brugeroplevelsen (blokeres skrivningen i devtools, virker appen uændret). Dashboardet rammer kun de fire aggregerede RPC'er, aldrig rå/live-tabeller. Ingen ny cron, intet materialized view.

Engangsopsætning: kør `sql/analytics_events.sql` og derefter `sql/analytics_dashboard.sql` i Supabase ("Run without RLS"). Den anden fil er, modsat den første, sikker og forventet at blive gen-kørt. Efter 30. juli 2026-ændringerne (Liga-diagnose + de to nye RPC'er + push-effekt) skal den gen-køres sammen med frontend-mergen; en gammel klient mod en ny RPC (eller omvendt) viser en tom liga-sektion, ikke forkerte tal.
